stwo-tensor vs FlashProve

A provable integer-inference prover built over 12 hours on stwo-zig (M31/QM31, multilinear Ligero-style PCS, LogUp-GKR), benchmarked against Anthropic's FlashProve. Same-relation runs use FlashProve's own sequential CPU prover, built and timed on this machine. FlashProve's H100 model-scale figures are quoted, not reproduced.

Security accounting, defined as FlashProve defines it

Our calculator (security.zig) sums every error term of the proof as implemented:

  • PCS queries per level, proximity, OOD collisions;
  • LogUp, sized by key degree and count;
  • GKR, charged per layer and per round;
  • every sumcheck and batching challenge;
  • proof-of-work.

Its "all rounds added" figure corresponds to FlashProve's 119.38 / 92.42 bits (with / without work). FlashProve's headline 126.21 / 96.23 is a different reading: the compiled bound N/2L as one number. The calculator's output was itself adversarially reviewed and corrected (SEC-1 to SEC-8).

Per-request serving

Every request gets its own proof: witness commitment, LogUp-GKR, sumchecks and witness opening. One weight opening shared by the batch covers all requests' weight claims after a cross-request reduction. This matches FlashProve's "a batch opens its copy once for all requests". The statement proves that the claimed next token is the greedy choice (least maximiser over the vocabulary), as in FlashProve's exact-match policy.

Measured on a 2-layer dense+MoE stack with LM head, 104M weights, 256 tokens:

  • Throughput: 159-227 tokens/s for batches of 1-4.
  • Proof per request: 375-530 KB, verified in about 18 ms.
  • Scaling coefficients and a compute-only Maverick extrapolation are in serving.md: about 550-1,840 s per request on this Mac's CPU.

Adversarial review

Two review phases ran in parallel worktrees. In each, reviewers built cheating provers, and an independent skeptic re-ran every finding and tried to refute it. Every confirmed finding then went to a fix stream with a regression test, followed by a separate re-checker that tried variants of each attack.

phase A · core, PCS, transformer, kernels, parity32 findings29 confirmed (1 critical, 6 high), 3 plausible
phase B · serving, calculator, zero knowledge20 findings19 confirmed (4 high), 1 plausible
  • Critical, fixed: the softmax reciprocal could wrap modulo p at 256+ tokens and accept a cheating attention output. Softmax now uses an exact accumulation and a division inequality.
  • High, fixed:
    • Weight openings were bound to the key only within unique decoding, so a hybrid committed word could open as a different model. Fixed with a key OOD claim plus per-batch proximity.
    • Statement bounds were inferred from sliced or summed keys.
    • No public input/output binding in non-hiding mode.
    • Shifts were chosen from the data. A model configuration now fixes them and is hashed into the statement.
    • Three zero-knowledge leaks: shared pads, a base-field-only GKR blinder, shared weight pad rows.
    • The embedding was not committed.
  • Re-checker catches: variants that escaped the first fixes:
    • a requant einsum treated as boolean;
    • partial-coverage bounds in the kernels;
    • LM statement-graph edits.
    All three are fixed. For the third, the verifier now rebuilds the whole request statement (ops, labels, tables, shifts, publics, model digest) from the model descriptor, prompt and claimed token, and never reads a statement from the prover. A second independent re-checker then tried 10 further attacks: deleted, reordered or relabelled ops, redirected inputs, altered tables, changed shifts and capacities. All were rejected.
  • Not fixed, documented: weight-hiding opening budget at serving scale, integer fidelity, and LogUp relations above p (rejected rather than chunked).

Round 3: Lean proofs

formal/tensor-frontend/ is about 1,340 lines of Lean on core v4.35.0 only. There is no sorry and no new axiom. scripts/check.sh audits 24 headline theorems and accepts only the standard axioms (propext, Classical.choice, Quot.sound). It runs with zig build lean.

    • End-to-end protocol soundness, zero knowledge, a Lean verifier, and a Lean-to-Zig refinement (each theorem matches its Zig code only by reading).
    • The bounds fixpoint algorithm itself, multi-column LogUp keys, GKR layering, the QM31 construction, and the PCS proximity terms.

Round 3: accuracy against a float model

We used the public checkpoint stories260K (Llama architecture, 5 layers, dim 64, GQA, RMSNorm, RoPE, SwiGLU). A float32 numpy reference was checked against an independent run.c re-implementation, with logits within 1.4e-5. The integer model is our proved model: the Zig integer forward matches bit for bit on all 238 kept windows, and 4 requests were proved, verified and rejected with a wrong token.

Eval: 256 held-out windows of 64 tokens (16,384 positions). The shift plan was calibrated on 64 separate windows. Agreement figures count refused windows as disagreements.

Round 3: selectable security level

A build-time challenge field: QM31 (default) or the degree-8 OM31 (|F| ≈ 2248). Levels bits128 and bits160 set queries, OOD and proof-of-work together. The level is written into the wire header, and the verifier rejects a mismatch. Default configurations and pinned digests are unchanged.

Round 3: CUDA backend

src/tensor/cuda/ has 19 kernels: lazy M31/QM31, int8 × QM31 weight fold, eq tables, fused multi-claim sumcheck rounds, batched LogUp-GKR layers, circle-FFT RS encode and Blake2s Merkle. There is also a C ABI host layer and a Zig backend behind -Dcuda=true, off by default. The design draws on PR #314 (residency, the GKR launch-count problem) and FlashProve's .cuh files (lazy reduction, weight-fold layouts, hashing lanes).

  • Verified here:
    • zig build test-cuda-emu compiles the exact kernel and host sources as C++ and checks them bit for bit against the CPU prover (14/14 tests).
    • Proof digests for the toy, MLP, layer and MoE model are the same through the emulated backend.
    • All 19 kernels lower to PTX for sm_90 and sm_120 via clang.
  • Measured in emulation (launches per proof): toy 49, MLP 91, decoder layer 313, 2-layer MoE 755. Batched GKR is projected at about 500 launches, against about 24k with one launch per instance.
  • Not yet resident:
    • The tiny MoE model still moves 98 MB to the device and 51 MB back. Witness generation, materialised sumcheck factors and Merkle nodes still pass through the host.
    • GKR is not yet wired to the device.
    • The matmul is a reference int64 kernel (no dp4a/IMMA), and there are no CUDA graphs.
  • Projected, not measured: decoder layer at 1024 tokens ≈ 0.3 s on an H100 and 0.5 s on an RTX 5090 once fully resident. A Maverick request at 70-240 s on one H100, against FlashProve's 9.2 s. The gap is witness volume, not kernel speed.
  • Untested: nothing has gone through nvcc or run on an NVIDIA GPU. scripts/tensor_cuda_*.sh are the first-run plan: build, tests, compute-sanitizer, and digest comparison against the CPU.

Open items

  • LM requests: the verifier builds the statement with a shape-only forward pass, so verifier memory grows with the witness. A builder without values is not done. The model digest is pinned next to the weight key rather than inside it. Shift plans are calibrated on random windows; a deployment would calibrate on representative inputs.
  • Model scale: streaming weights and witness per layer, GKR instance merging, and a CUDA port before any H100-class comparison.
  • Security: ZK and Metal for the OM31 build; the memory growth at OM31; hiding openings in the calculator.
  • Lean: end-to-end soundness, ZK, GKR layering, and a Lean-to-Zig refinement or Lean verifier.
  • Accuracy: wide activations and residuals in the prover (needs the K ≤ 12 bound redesign), a saturating requant to stop refusals, and a larger checkpoint.
  • CUDA: first nvcc build and GPU run, device witness generation, device GKR, IMMA matmul, CUDA graphs.
