# S31 MVP roadmap and prototype status

Status: linked-chip, sparse-arithmetic, direct-M31, a narrow private repeated-step boundary, personalized BLAKE2s, pinned field-native Poseidon2 tree functions, a limited typed text frontend, three one-header SHA proof profiles, and recursive Bitcoin-chain prototypes implemented, 2026-10-07. The [S31 compiler](../../src/frontends/s31/README.md) builds a prover, sealed native verifier, typed public ABI, and reproducible package. The [text language guide](../../src/frontends/s31/docs/reference/TEXT_LANGUAGE.md), [source-to-AIR guide](../../src/frontends/s31/docs/reference/LANGUAGE_AND_AIR.md), [private boundary guide](../../src/frontends/s31/docs/private-boundary.md), and [recursive-chain walkthrough](../../src/frontends/s31/docs/recursion-chain.md) give executable syntax examples and the exact proof relations. The design and exit gates below remain the standard for calling this a general MVP; implementation status is summarized here so planned work is not mistaken for delivered work.

## What works now

- A limited typed `.s31` frontend accepts declarations, immutable `let`, pure function calls, static `iterate`, nominal hash digests, constrained bit selection, and fixed-depth Merkle path composition. It lowers through normalized JSON to the existing compiler. The [text acceptance script](../../src/frontends/s31/tests/acceptance/acceptance_text_v1.py) checks that recurrence and Poseidon2 path programs match handwritten relations in canonical IR and cost geometry, and that both forms pass generated native verifiers. A complete language frontend remains future work.
- `gate` keeps the original eleven-component circuit proof (`S31NAT1`). `chip` adds a four-lane indexed repeated-step AIR to **one** combined STARK proof (`S31NAT2`). The chip has nine base columns, eight interaction columns, four transition equations and two LogUp equations per row. The native verifier checks the circuit and chip lookup closures and passes all twelve components to one core verifier call.
- `sparse-gate` and `sparse-chip` use `sparse-v3` (`S31NAT3G/C`). Their circuit portion has three active components and 12 preprocessed columns. The arithmetic profile rejects Eq, XOR and Blake-G gates. The sparse-chip proof additionally carries the step component. Profile-specific identities, proof envelopes, keys and verifier paths prevent cross-profile decoding.
- The first chip shape is exactly one public four-lane `x ← x²+c` repeat with 16–32768 power-of-two rounds. Four valid package shapes at 16, 256, 4096 and 32768 rounds have been proved and independently verified under both sparse modes. A [machine-readable seven-trial profile record](measurements/language/profiles-v2-2026-10-06.json) captures distinct valid inputs per trial and the exact proof artifacts.
- The [profile acceptance run](measurements/language/profile-acceptance-v2-2026-10-06.json) verifies the same 256-round statement under all four profiles, rejects changed public outputs, altered keys, damaged proofs, and cross-profile replay, and rejects seven precommitment chip-witness mutations: first input, middle output, duplicate index, last output, wrong constant, interaction cell, and claimed sum.
- `direct-gate` and `direct-chip` use `direct-m31-v4` (`S31NAT4G/C`) for all-M31 arithmetic programs. Public M31 values are bound directly and checked for canonical encoding by the native verifier. Only the QM31 arithmetic circuit component and eight preprocessed columns remain; the M31-to-u32 and range-16 components and the 65,536-row sequence table disappear. The [direct acceptance run](measurements/language/direct-acceptance-v4-2026-10-06.json) proves one M31 source under sparse-v3 and direct-v4, rejects cross-profile replay and public/key/proof changes, and rejects seven chip-witness mutations under both chip profiles.
- The `gate` profile now has domain-separated BLAKE2s leaf and ordered-pair nodes plus a Boolean-constrained M31 array selector. The [hash suite acceptance record](measurements/hash/hash-suite-acceptance-v5-2026-10-06.json) checks an independently computed two-leaf root and a one-level private Merkle path against generated native verifiers. A parent hash of two eight-word reduced digests uses one Blake2s block because domain separation lives in the personalization parameter. This is a functional extension, not a new efficient hash proof profile: the examples still commit about 4.26 million preprocessed cells and produce roughly 460–472 KB proofs.
- `hash_poseidon2_leaf` and `hash_poseidon2_pair` reuse the repository's pinned Stark-V M31 permutation and recursion-channel Merkle framing. They lower through `direct-gate` into the single QM31 arithmetic AIR component. A private selector input is constrained by its sole producing gate `b²=b`, so one-level Merkle paths use no Eq or bitwise component. The [Poseidon2 acceptance run](measurements/hash/poseidon-acceptance-v6-2026-10-06.json) verifies two-leaf and path proofs under generated native verifiers, both branch directions, an independent Python arithmetic oracle, and nine rejection cases. This is a generic arithmetic circuit path, not a dedicated Poseidon2 chip.
- The compiler-owned `std@1` math layer includes fixed-array lane sums and dot products. A constrained QM31 projection replaced per-coordinate unpacking in `sum_lanes`; the [historical 64-lane comparison](measurements/language/packed-reduction-2026-10-06.json) records that step. Private M31 arrays now enter as packed QM31 witnesses. On a 128-lane reduction, [seven matched witnesses](measurements/language/packed-inputs-2026-10-06.json) reduced raw QM31 rows from 650 to 361, padded rows from 1,024 to 512, and median proof size from 72,944 to 55,719 bytes. Median prover time excluding logged PoW fell from 2.305 to 1.490 ms; whole-process timing did not improve in that noisy sample. The native verifiers accepted valid proofs and rejected changed public output. `s31 oracle` independently checks arithmetic, BLAKE2s, and Poseidon2 values without a proof; `s31 trial` records source-to-proof geometry, oracle status, native verification, and changed-statement rejection. Package inspection re-lowers text against its sealed relation. `s31 tune` compares explicit profiles on the same assignment corpus without auto-selecting one.
- A `gate` package now seals two recursive wrapper keys. The [two-level acceptance fixture](../../src/frontends/s31/tests/acceptance/acceptance_recursion_chain.py) proves a private-witness leaf, verifies its first wrapper inside a second circuit, and accepts the top proof after both lower proof files are removed. It checks a first-level digest containing raw `u32` words above the M31 modulus, seven direct second-level verifier mutations, seven external corruptions, and byte-identical top proofs under the normal and low-memory proving policies. The [single-machine record](measurements/recursion/recursion-chain-v1-2026-10-07.json) reports a 555,050-byte arith4 top proof, 3.89 seconds and 9.31 GB for its second wrap, 4.38 seconds and 7.00 GB under the low-memory policy, and 0.07 seconds and 205 MB for standalone native top verification. The wrapper keys are depth-specific; this is not an indefinite fixed-key fold.
- `sparse-wide-gate` packages now seal `K0`, two depth-specific verifier keys, and a repeatable fixed-fold key. The [worked sparse-wide fold](../../src/frontends/s31/docs/recursion-wide-fold.md) proves a wide-integer or two-header Bitcoin leaf, wraps it twice, then uses one AIR/key for repeated proof verification. Its acceptance fixture challenges circuit witnesses and repaired public claims, and verifies the top proof after lower proofs are removed. The [performance map](recursion/RECURSION_PERFORMANCE.md#same-key-sparse-wide-claim-fold) records constant-size proof artifacts and the cost of this bridge. A one-header checked ChainWork transition exists separately; a growing chain still requires authenticated prior state and integration of that transition with the repeatable fold.
- `sha-shift` and `sha-fused` package byte-exact SHA256d of one private Bitcoin header in a single circuit-plus-chip proof, with generated native verifiers and profile-specific sealed keys. A [three-header matched production run](bitcoin/BITCOIN_MULTI_WITNESS_BENCH.md) verified 45 proofs and found per-header median proving work excluding both PoW grinds near 153–154 ms for generic, 43 ms for shift v3, and 39 ms for fused v4. Fused v4 also produced smaller proofs than v3 and verified faster. Total prover times varied sharply with the deterministic FRI nonce search and do not establish an end-to-end throughput ranking. The [fused AIR design](sha/SHA_FUSED_AIR_PLAN.md) records its layout and soundness obligations.
- `direct-m31-private-v5` connects one private four-lane repeated-step input and output to the circuit through an authenticated Gate and indexed chip lookup in one proof. The source fixes eight endpoint addresses; the sealed key and native verifier recompile and bind them. The [boundary guide](../../src/frontends/s31/docs/private-boundary.md) describes the exact source shape and privacy limit. The [focused package acceptance](../../src/frontends/s31/tests/acceptance/acceptance_private_boundary.py) checks a public-only claim, a native proof, and changed source, key, input, claim, and proof bytes. This is a constrained first private boundary, not arbitrary chip extraction.
- `std::math::sum_u256` and `sum_u256_checked` lower a static array of up to 16 `UInt256` values to a balanced tree of proved 256-bit additions. The [wide-value guide](../../src/frontends/s31/docs/wide-values.md) and [measurement record](measurements/language/u256-static-sum-v1-2026-10-07.json) show checked overflow behavior, three native proof examples, and unchanged padded AIR geometry against explicit addition.
- The source library has distinct `Target`, `Work`, and `ChainWork` types. The [one-header ChainWork program](../../src/frontends/s31/examples/bitcoin/bitcoin_chainwork_step.s31) derives its target from a private mainnet header, checks SHA256d proof of work, proves block work, performs checked accumulation, and publishes a Poseidon2 commitment to the prior and next work plus header hash. Its [native acceptance](../../src/frontends/s31/tests/acceptance/acceptance_bitcoin_chainwork_step.py) checks an independent Bitcoin/Poseidon oracle and rejects invalid work, overflow, changed claims and prior state, proof tampering, and key tampering. The [cost record](measurements/bitcoin/bitcoin-chainwork-step-mvp-2026-10-07.json) reports 380,404 raw QM31 rows and a 335,467-byte proof from one generic-circuit run; these are not throughput estimates. Authenticating the prior checkpoint and joining this transition to a repeatable recursive fold remain open.

The focused `std@1` library has a [single native-proof release gate](../../src/frontends/s31/tests/acceptance/library_mvp_gate.py) and [pinned AIR cost baseline](../../src/frontends/s31/tests/acceptance/library_mvp_cost_baseline.json) for representative math, field division, wide addition, BLAKE2s, array, Boolean, and Bitcoin ChainWork programs. This is a supported subset. The [next integer-family contract](language/FIXED_WIDTH_INTEGERS.md) specifies `u8` through `u128` and `i8` through `i128`; those scalar types are not yet implemented.

The [three-trial hash baseline](measurements/hash/hash-suite-benchmark-v5-2026-10-06.json) used distinct private inputs and native verification for every proof. The two-leaf tree used 240 Blake-G rows and had 0.632 s median proving, 0.051 s cold setup and a 464,630-byte median proof. The one-level path used 160 Blake-G rows plus two selector Eq rows and had 0.444 s median proving, 0.054 s cold setup and a 466,687-byte median proof. Proof-of-work is included in proving and was not separated in this full-circuit run; these numbers provide a baseline, not a statistically stable difference between functions.

The [five-trial same-shape comparison](measurements/hash/poseidon-comparison-v6-2026-10-06.json) reran BLAKE2s under the current compiler and compared it to Poseidon2 on the same private arrays and tree topology. For two leaves plus parent, fixed cells fell from 4,255,616 to 131,072, median proof from 464,630 to 164,333 bytes, and median proving from 0.553 to 0.0745 seconds. For a one-level private path, cells fell from 4,255,440 to 65,536, proof from 471,736 to 136,331 bytes, and proving from 0.480 to 0.123 seconds. These are different hash functions with different outputs and security assumptions; the timing ratios include stochastic proof-of-work and are sample medians.

## Decision: version every proof profile

Keep `circuit-v1` byte compatible with the pinned eleven-component Stwo circuit proof. `hybrid-step-v2` adds one repeated-step AIR chip to it; `sparse-v3` keeps the three arithmetic/range components; `direct-m31-v4` keeps only the QM31 arithmetic component and uses a canonical M31 public ABI. A verifier must reject an unknown profile before decoding its STARK proof. Each key pins the profile, source and canonical IR hashes, chip parameters, component geometry, public ABI, preprocessed root, PCS/FRI settings, channel and proof size limit. The profile tag, source digest and circuit identity enter the Fiat–Shamir transcript before the base commitment. A fully explicit generated component manifest remains a next step.

The native verifier now recompiles its embedded source with the selected
profile and requires the key's padded geometry, preprocessed root, circuit
hash, and trace log to match. A [forged-key regression](../../src/frontends/s31/tests/acceptance/acceptance_key_binding.py)
changes an affine constant and gives the source-A verifier source-B circuit
commitments; the verifier rejects B's valid proof. Fresh proofs pass under all
six profiles. Recomputing this binding costs verification time: for one
256-round full-gate example, ten interleaved process runs had 72.19 ms
median with the check and 15.80 ms with only that check removed. Proof
generation is unaffected. The [exploratory measurement](measurements/language/key-binding-verifier-overhead-2026-10-06.json)
records the ten interleaved samples, build differences, and artifact hashes.
A future batch-verifier context can amortize
source compilation when many proofs use one key. The package manifest is
unsigned; verifier binary and key authenticity still require trusted
distribution.

The first chip is deliberately narrow: four M31 inputs, four M31 outputs, a power-of-two number of rounds from 16 through 32768, and `x[j] ← x[j]^2 + c` for each of the four lanes. This is exactly the workload in the existing [scaled comparison](README.md#scaled-circuit-comparison). `c` and the round count are compile-time constants in the verification key. The initial profiles share public endpoints; `direct-m31-private-v5` additionally authenticates one private pair of four-lane endpoints. Arbitrary repeat bodies and automatic extraction remain future work.

## Milestone A — one linked chip in one proof

The gate lowering proves the existing unrolled circuit. The chip lowering replaces that repeat region with a four-lane output witness in the circuit. The circuit still binds the same eight public values through its existing output gates. The chip proves the recurrence over a trace of `R` rows and binds to those exact public values through an independent, domain-separated relation. The verifier reconstructs both AIR component sets and calls `core.verifier` once against one transcript, one base commitment, one interaction commitment, and one FRI proof. It must never accept two separately verified STARKs as a hybrid proof.

Each chip row contains an index `i`, four `in` values and four `out` values, all M31. Four algebraic constraints enforce `out[j] = in[j]^2 + c`. The row emits a positive lookup for `(CHIP_DOMAIN, i, in[0..4])` and a negative lookup for `(CHIP_DOMAIN, i+1, out[0..4])`. It uses the same transcript-drawn extension-field `z, α` as the circuit's LogUp system and two secure interaction columns: the first fraction and a centered cumulative sum. The verifier adds public endpoint terms with opposite signs for `(CHIP_DOMAIN, 0, x[0..4])` and `(CHIP_DOMAIN, R, y[0..4])`, then requires the chip's claimed sum plus those terms to be zero. The circuit's original Gate relation still closes independently. Public `x` and `y` are common to both closures, so the chip and circuit agree on the boundary.

The index is a **committed witness value**. The lookup tuple includes it and each row uses `i+1` for its output, while there are exactly `R` rows and public endpoints at `0` and `R`. This permits a multiset argument without a next-row selector. The soundness argument must account for the lookup compression collision probability and M31 index wrap; `R < p` and the endpoint path `0..R` cannot wrap. The implementation must reject zero lookup denominators and noncanonical field encodings. The chip's `R`, `c`, relation domain, trace width, and component order are key-bound and transcript-bound. A formal or symbolic review should prove that a balanced size-`R` multiset containing the endpoint path has no room for disconnected cycles, under collision-free tuple compression.

**Implemented engineering sequence**

1. Write the chip witness and AIR component as one reviewed module with shared row equations; generate base and LogUp columns, domain and OOD quotients, and a direct scalar oracle. Pin the four-lane tuple order.
2. Extend the circuit prover with an optional chip extension. Append its 9 base and 8 interaction columns to the existing trees, add its claimed sum to the transcript, and append the chip AIR to the component list. Keep the old profile entry point byte compatible.
3. Introduce a `S31NAT2` envelope and separate native verifier path. It reconstructs both tree geometries, checks both lookup closures, checks the key and transcript domain, and invokes the core verifier on the complete component list. Generate this verifier in every chip package.
4. Add an explicit compiler selection `--lowering=gate|chip`; reject chip mode unless the relation matches the supported shape. Keep auto selection disabled until cost crossover data exists.
5. Prove the same statements at 16, 256, 4096, and 32768 rounds with both lowerings. Test chip witness mutations **before commitment**: wrong first/last value, wrong middle value, duplicate/skipped index, wrong constant, changed claimed sum, and malformed interaction column. Every malformed witness must either fail proving or yield a proof the native verifier rejects. Also mutate proof metadata and public values after proving.

**Exit gate:** both lowerings produce the same outputs; both native verifiers accept valid proofs; all semantic witness mutations reject; the hybrid proof has exactly one PCS/FRI instance; and a documented cost table covers cold setup, cached setup, proving, verification, proof bytes, peak memory, and the existing equivalent Cairo function. The single-proof architecture, valid arithmetic profile matrix, listed adversarial/cross-profile tests, one constrained mixed private-boundary relation, and a matched recurrence Cairo run are implemented. Repeated memory measurements, a generated manifest and independent soundness review remain open. No claimed speedup is published from raw AIR row counts alone.

## Milestone B — sparse circuit profile

The pinned circuit AIR always includes eleven components and 45 preprocessed columns. Its fixed XOR tables alone account for roughly 4.18 million preprocessed cells, even when a relation does no XOR. `sparse-v3` must create a **new protocol**, not simply omit columns while keeping the old circuit hash. The first sparse case is the four-lane M31 recurrence without Blake2s or private range-restricted inputs. A direct M31 public ABI can bind `(x,0,0,0)` to a public output gate, avoiding the M31-to-u32 conversion and 16-bit range table. Public M31 values are checked to be canonical by the native verifier.

A generated manifest lists active components, their order and log sizes, preprocessed column IDs and lengths, fixed-table digests, relation domains, trace widths and constraint-program hashes. Prover and verifier derive tree geometry, circuit identity, claimed-sum count and composition ordering from this manifest. An inactive component contributes **zero** columns, no claimed sum and no constraints. The AIR binder must rebase preprocessed indices and composition random-coefficient offsets after filtering. A structural dependency pass rejects a profile if a selected component emits a lookup into a relation without the needed producer/table, unless a separately reviewed argument proves that relation closes by another route. Empty and all-zero components receive explicit treatment; no implicit padding may resurrect omitted tables.

The implemented sparse-v3 target removes the Blake-G, triple-XOR and all XOR table components and their fixed columns. Its `u32` public binding still requires M31-to-u32 and the 16-bit range table, even for an M31-only program. Direct-M31 v4 removes those last two components for all-M31 arithmetic sources under a separately versioned public ABI. Hash relations currently stay on the full profile. The compiler selects the profile from typed operations and range obligations, not from witness values.

**Exit gate:** a verifier built from the key rejects altered component manifests, missing needed tables, changed fixed-table values, reordered components, changed public ABI and cross-profile proof replay. Gate-only and chip programs under `sparse-v3` and `direct-m31-v4` match their full-profile semantics on a shared corpus. The [consistency note](security/PROFILE_SOUNDNESS.md) enumerates each active relation's producers and consumers, the public boundary argument and transcript binding. Cold and cached timings must show the effect separately; the old profile remains readable. The arithmetic component sets, native proof verification and profile envelopes are implemented; a fully explicit generated manifest and independent soundness review remain open.

## Milestone C — promote into a useful MVP

`s31 tune` now builds explicitly requested lowerings for one source and a
shared assignment corpus, then records proof bytes, raw/padded geometry,
native verifier results, wall time, logged non-PoW prover time, and the host
profile. It does not select a lowering. The remaining cost model must account
for measured base/interaction/preprocessed cells, FRI work, lookup count,
PoW variance, proof size, verifier cost, and cache policy. `s31 inspect`
reports profile geometry, while a richer per-region gate/chip decision report
remains future work. Promote automatic chip extraction only at a measured
total-cost win, with a fallback to gate lowering. Generalize the chip to
multiple static step bodies and more than one instance only after its
boundary argument is reviewed. Extend the authenticated private endpoint
bridge beyond one four-lane recurrence to multiple instances and other chips;
the current profile proves only this fixed private source shape.

The deliverable deserving the name **MVP** is a single command that builds a sealed prover and independent native verifier, proves and verifies a mixed relation with a circuit region and at least one chip in one proof, handles sparse and direct arithmetic profiles, and reports a reproducible matched Cairo comparison. The present prototype satisfies the packaging, specialized linked chip, arithmetic sparse profile, direct-M31 ABI, one narrow private boundary, and one matched current-profile Cairo comparison. General mixed private relations still need a reviewed boundary model, a generated component manifest, broader adversarial evidence and a reliable cost model.

The field-native circuit candidate now has pinned constants, explicit leaf and parent framing, an independent arithmetic oracle, generated native verifiers, and a measured crossover against BLAKE2s. A collision/security review remains open. BLAKE2s still needs a hash-specific sparse profile with Blake-G, XOR, conversion and range dependency closure. Poseidon2 still needs a dedicated batched hash AIR if generic circuit rows become the limiting cost at larger depths.

The next field-native research path is to adapt the [Stwo Poseidon2 AIR example](https://github.com/starkware-libs/stwo/tree/dev/crates/examples/src/poseidon) to the repository's pinned Stark-V parameters and S31's specified sponge/parent construction. The chip must join the existing circuit in one proof, bind private inputs and public roots through the same lookup argument, reconstruct its AIR in the generated native verifier, and pass adversarial trace-mutation tests. The currently implemented direct circuit is the correctness and cost baseline for that work.

For the broader function suite, prioritize by shared proof infrastructure:

1. Promote constrained bit selection and canonical word encodings into reusable typed primitives; add a first-class fixed-depth Merkle path built from the proved leaf and ordered-pair semantics.
2. Add a batch Poseidon2 hash chip for the pinned sponge and parent construction, with circuit-to-chip boundary constraints, generated native verifier data, adversarial trace mutations and a measured crossover against the implemented direct circuit and BLAKE2s baseline.
3. Add commitment openings and common transcript encodings over those hashes. Keep external 256-bit byte digests distinct from reduced `m31[8]` digests in the type system.
4. Add SHA-256/Keccak or signature gadgets only against a concrete interoperability workload, with their own circuit/chip cost report. These functions must not silently inherit the arithmetic profile or the reduced-digest ABI.

## Measurement discipline

Use the same source-level function, public statement, machine, PoW/FRI parameters and output semantics for each comparison. Record witness generation, first-key preprocessing, cached preprocessing, prover stages, native verification, proof bytes and peak process memory. Run enough trials to report median and spread because PoW varies. A fixed-table saving is real only if the proof and native verifier both use the selected geometry. The 32,768-round gate trace has 65,853 raw field rows padded to 131,072; the linked chip has 32,768 rows and 17 committed base/interaction columns. The chip proof verifies in sparse-v3 and direct-M31-v4 geometry. The matched Cairo result above is for one recurrence; optimizing a different workload requires its own crossover measurement.
