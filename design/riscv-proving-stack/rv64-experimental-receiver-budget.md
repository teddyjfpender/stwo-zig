# Experimental Ethereum receiver hard allocation budget

The experimental OM/GKR CLI receiver selects a stable `SharedHostBudget` before reading config, image, program metadata, immutable source keys, candidate fixed setup or the proof bundle. This closes the prior gap where `FIXED_SETUP_BYTES` bounded only the beta2 cache after legacy source-key construction had already happened.

Both control and candidate fresh verification default to 32 GiB of requested-live allocation authority. An optional final `RECEIVER_BYTES` argument overrides it; zero, malformed or extra arguments fail before opening the config. Existing commands remain valid. Producer/plan allocation paths, proof parameters, statements and proof bytes are unchanged. The existing `FIXED_SETUP_BYTES` is still a nested candidate-cache cap and cannot authorize allocation beyond the outer receiver budget.

This is not an RSS bound. The recycler beneath the live allocation budget has a 4 GiB free-list cache cap. That cap excludes live allocations; capacity rounding and resize retention can make physical backing exceed requested bytes. Worker pthread stacks are separately bounded by the configured pool (at most worker-count times 1 MiB); the caller stack, allocator/OS bookkeeping and executable mappings are additional process overhead. CLI argument storage and the stable budget control block are small allocations outside the receiver owner. There is no new process-wide cache. Layer allocation sees the actual shared-budget allocator and therefore preserves its cap instead of selecting the unbudgeted mmap route.

Ownership order matters: args use the recycler, the budget heap object is created next, and all receiver-backed defers run before `budget.destroy()`, args cleanup and recycler teardown. Existing nested setup/cache/tree leases retain the same owner. A budget refusal remains typed `OutOfMemory`; it cannot choose a smaller security profile or turn acceptance into success.

The existing actual five-proof beta2 fixture now independently constructs fresh trusted keys, its own candidate cache/authority and verifies under a single shared 8 GiB owner. A separate 1 MiB cap interrupts partially constructed source setup and checks that requested-live allocation returns to zero before owner destruction. The earlier source-shape preflight still runs before expensive keys. Neither a passing resource gate nor the candidate label is a reviewed whole-128 certificate.
