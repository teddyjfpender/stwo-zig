# M7 global memory admission API

Status: **isolated runtime guard qualified; whole-request admission pending**. The combined driver builds, six ledger/endpoint tests pass, and fourteen actual GPU guard cases pass with a 22 GiB arena and poison 165. Three expected owner NVTX ranges were captured. Receipts are in `vectors/reports/rv64-m7-20261105/admission/runtime-qualification.json`. These checks do not qualify native GKR, outer GKR, early scheduling, or a full request.

One `global_admission.Planner` belongs to the physical GPU pool and covers every session on those GPUs. `Preset` accepts only 16G/18G/20G/22G; automatic arenas are refused. It budgets a 4 GiB external allowance and a 512 MiB small slab. Each actual large allocation rounds independently to 32 MiB; small allocations round to 512 bytes. Call `Footprint.allocations` with the actual allocation list, including native GKR decoded sources, workspace, twiddles, status, seed and each parameter slab. Existing MAIN/FIXED/coefficient owners and immutable caches remain additional live allocations. Aliases are counted at their allocation owner. Retired contexts remain charged until physical destruction.

The runtime endpoint observes global arena live bytes across all native contexts. It never infers retention from one session's counters. In this mode, demand `retained_new` is zero and `temporary` covers **every additional simultaneous allocation**, including outputs retained after the callback. `completeObserved` reconciles the actual post-cleanup global allocation total. The successor claim covers consumer new retained allocations **plus** its maximum following scratch while the source is still live; scratch alone is insufficient. Wide stages serialize per physical GPU. Unknown device or host costs refuse admission.

`Endpoint.tryReserve` runs on a host caller and returns without waiting. It locks the physical stage gate, queries the owner-thread arena snapshot, checks the static preset and external allowance, samples process RSS, and reserves the envelope. The owner callback calls `Permit.enterOwner` immediately before GPU mutation, and `leaveOwner` only after all transient releases and joins. The host calls `finish` after submit returns. The C allocator requires the matching context and ticket and checks rounded global live bytes against the envelope before allocation. A foreign context cannot borrow a permit. Graph capture pool allocation is refused while enforcement is enabled. Missing or stale permits cannot allocate.

Runtime permits produce `m7/{domain}/{stage}/r{request}/o{ordinal}/t{ticket}` NVTX ranges and `GLOBAL_ADMISSION_STAGE` logs with owner queue and callback durations. They will allow actual per-stage GPU interval accounting when all production stages are wrapped. The existing ownership capture uses the previously qualified v3 driver and has no inner stage NVTX ranges; it must not be presented as such.

The host budget is 20 GiB. Admission adds sampled process RSS, all active host claims, and the new stage's declared additional peak. This conservative bound may double-count active allocations already visible in RSS; it cannot undercharge them. CPU preparation still needs its own reservation hook. A chunk design with a 16.5 GB host frontier cannot be admitted merely because its device slots fit. An unavailable numerical implementation remains unavailable regardless of modeled cost.

`STWO_RV64_GLOBAL_ADMISSION=1` opts into Pool configuration and requires an explicit static arena preset. Default behavior is unchanged. Configuring endpoints does **not** enable early scheduling: `Factory.memory_admission_enabled` becomes true only when every physical device is configured, healthy, and has every required stage cost registered. Cost coverage defaults to empty. The current production stages are not yet wrapped, so this option deliberately refuses their unreserved allocations; it is not a usable full-request profile yet.

Scheduler retries must occur outside GPU owner callbacks and outside phase/cache locks. A blocked native producer must yield so an already-ready recursion consumer can run and retire retention. `execution_wrap` owns the separate ready-consumer queue gate; host preparation quotas and ROOTCHECK still wait for native completion. Proof-scope cleanup has a checked variant; a failed owner submission poisons the planner and cannot retire a claim. Future-claim tokens may be released only after the corresponding physical owner destruction. Failure with an unresolved owner keeps that physical endpoint terminal until teardown.

Remaining gates: stage allocation and host bounds for native source/MAIN/INTER/TC/RC/PCS, recursion values/MAIN/INTER/TC/RC/PCS, immutable setup and selected GKR modes; producer retry and last-use retirement tables; CPU-preparation reservations; all-context coverage audit; both development blocks with complete M6 artifact parity and fresh receivers under interleaved scheduling. The currently qualified v3 process exceeds 20 GiB RSS, so host memory reduction is also required before this target can pass.
