# OP R6 independent OM31 multiplication

The R5 actual-small-block control is retained at `bf90b4567` with its receiver
binary and complete persisted artifacts. R6 is an explicit experimental outer
schema, not a default switch. It uses `STP26G01` and a source-derived semantic
identity distinct from R5. It does not change the inner native OP protocol,
external program/block identities or the expected execution endpoint.

A genuine full OM31 product previously lowered to seven QM31 arithmetic rows.
R6 reserves its two QM31 output variables once and proves the product in a
separate independently sized table: 24 MAIN, 9 FIXED and 24 INTER columns. Eight
base-coordinate quadratic equations establish the exact existing native tower
product. Six complete QM31 Var tuples authenticate four input and two output
ports, including all extension coordinates, source variable IDs and output use
counts. Three paired cumulative OM31 fractions share a vertical accumulator;
all constraints remain degree three or less on a 2n quotient. The complete
six-component Var and range sum, including public outputs, is checked natively
and inside the recursive verifier. No port is a guessed self-yield.

Immutable inner-field shortcuts remain ahead of the opt-in product hook. The
hook is scoped explicitly; old code uses the original lowering. Trace and actual
circuits record the same source graph. An old five-component key rejects new
sidecar producers. Hash identity commits the actual multiplication coefficient
tensor, complete port recipe, old pinned AIR, P2 authority, source FIXED root,
all ordered native heights and output arity, rather than witness/prover files.

The first focused ReleaseSafe runtime gate passes a real six-component 530,608
byte proof, a fresh source receiver, full numerical recursive verification and
physical/adversarial mutations. This is a tiny correctness fixture. It is not
an OP block speed measurement or a completed root admission path.

The reason to test this architecture is padding, not only arithmetic count.
The actual R5 source census has CPU 4,818,570 QM31 rows and SHA 4,426,562 rows.
Their full-product lowering accounts for 825,659 and 517,567 rows respectively.
If extraction preserves those counts, their tall table drops below 2^22 while
native products occupy their own smaller table. The actual R6 source census now confirms CPU 3,992,911 rows and SHA
3,908,995 rows, both below 2^22. The actual small-block CPU physical leaf
passes independent reception; the measurements below apply only to that leaf. Keccak service-local
GKR is a separate cooperating workstream. Height-grouped PCS is not assumed to
remove width-times-height absorption: the existing lifted committer already
reuses native-height prefixes, and extra trees add authentication paths.

The security label remains **128-bit security target under documented
assumptions**, `security_qualified=false`; production admission remains closed.
Pending gates are full-height heavy source-shard census, combined service-local
GKR recursive leaf, complete fold/root and fresh durable receiver, then matched
full-block native-plus-root timings.

## Receiver-only key retention

The R6 source-only receiver releases each independently constructed key's raw
FIXED values, committed FIXED tree and witness-use array immediately after
source admission. It retains the source-derived semantic identity, FIXED root,
all geometry, output arity and bound constraint system. Parent topology
construction applies the same transition after each parent key is derived;
producer topology construction retains its proving data. This reduces retained
memory across many leaf classes but does not avoid the initial FIXED commitment
or claim a cold setup speedup.

`native_omul/verifier_key.zig` owns this explicit, idempotent transition. Native
verification and recursive statement construction consume the resulting narrow
key. Attempting to prove with it fails before witness allocation, including the
monolithic control path. R5 authority and proof sources remain untouched.
The focused physical proof gate verifies after retirement, exercises recursive
verification and rejects altered outputs and claims with the retired key. The
fold gate derives identical actual and source-only parent graphs from retired
child keys. Complete-block memory qualification remains a separate gate.

## Explicit truth-local admission

The R6 producer and final-root receiver expose `*WithOptions` entrypoints taking
`pure_p2_op_runtime.Options`. The caller must explicitly select
`truth_local_gkr=true` for schema2 source declarations; default wrappers retain
schema1. No sidecar field can silently choose the native protocol. Schema2 uses
local GKR for eligible Keccak/secp workers and preserves classic SHA and other
truths. Inventory derives each expected statement/key from independent source
keys. Service-local receipts are authenticated in the service leaf's public
frame; they remain outside the pre-challenge manifest's CPU-only local receipt
field because these service proofs are drawn after that manifest.

The complete physical gate is opt-in with `STWO_OP_R6_TRUTH_LOCAL=1`, alongside
`STWO_OP_R6_ROOT_CONFIG`, `STWO_OP_R6_ROOT_NATIVE`, and a fresh
`STWO_OP_R6_ROOT_OUT` directory. After persisting every node and final root, it
copies only `native-op.json` and `cells.bin` into `source-only`, checks that no
native proof file exists there, and reconstructs/qualifies the final root from
that source-only handoff. A flipped schema policy must reject before key setup.
The existing full terminal, ordered coverage, source-key substitution and
balanced-global-claim controls run on this same retained root.

Current measured CPU and isolated338-call Keccak leaves do not establish the
heavy tenfold target. Multiplying30-second CPU wraps by57 CPU shards and adding
folds would already exceed332 seconds. The complete-root gate must be followed
by real full-height class costing and an equal-security/workload comparison to
the retained M6/M7 route; pure P2 is not assumed to be the best CPU architecture.

## Explicit command-line reproduction

The root CLI retains R5/classic admission without flags. After producing a
schema2 native bundle with the explicitly selected service-local GKR protocol,
use the matching R6 root mode:

```sh
zig build rv64-op-root -Doptimize=ReleaseFast -j1
zig-out/bin/rv64-op-root --r6 --truth-local-gkr prove config.json native-directory root-directory
zig-out/bin/rv64-op-root --r6 --truth-local-gkr verify config.json source-only-directory root-directory
```

An optional final `resources.json` sets the common hard requested-live cap and
native source preparation limits. The root output directory must be new when
proving. A source-only directory needs only `native-op.json` and `cells.bin`;
verification never opens `native-op.bin`. The R6 proof, sidecar and GKR shape
files remain in the root directory. Omit `--truth-local-gkr` only for an explicit
classic-service R6 control. Local GKR without `--r6`, duplicate flags, unknown
flags and a receiver/schema mismatch reject. Neither flag changes Ethereum
profiles or imports a producer verifier key.
