## 4. What this means for the streams [D]

1. **Recursion is host-bound, not GPU-bound.**
   - Per lane, 66.8 s of span contains about 16.7 s of GPU work. The rest is serial host
     work on one thread per lane, out of 40 cores.
   - With host prep moved off the lane thread (prep pool, two-stage nodes), the lane
     bound becomes about max(GPU work, critical-path host):
     - GPU work summed over 33 nodes is ≈ 29.2 s, or ≈ 14.6 s per device [D].
     - Even with perfect overlap, the fold tail (12.7 s, 5 levels, about 2.0 s of host
       time per fold) stays on the critical path unless fold host work shrinks or arity
       grows.
2. **Fold tail: 12.7 s.**
   - The 5-level chain is serial, and each level is about 70% host.
   - Cutting fold host time, which is mostly wrap: preprocess, plan and verify, pays
     5× on the critical path.
3. **Launch- and sync-bound GPU stages.**
   - Assignment issues 1.93 M launches at about 3 µs of enqueue each, which is 8.8 s of
     host time against 3.65 s of device time.
   - 32.8 k stream syncs serialise host and GPU inside each node.
4. **Allocator.**
   - `cudaMallocFromPoolAsync` takes 4.0 s and `TrimTo` 0.8 s. Trimming between phases
     makes the pool re-grow from the driver.
   - Keep a retained arena per lane, or raise the release threshold during recursion.
     This is scheduling-only.
5. **The native stage is also mostly host.**
   - Kernel time from the first kernel to the start of recursion is only 1.5–2.5 s per
     device, across 17.3 s of native prove + verify.
   - Setup (13.5 s) and capture (4.7 s) do essentially no GPU work.
