# Cross-window caller arithmetic batching

The bounded original union removes repeated STARK machinery, but it still places a separate wide caller component inventory in the proof for each native window containing calls. It shares composition and FRI; it does not yet share arithmetic columns across those windows.

The current canonical single-window proof census attributes 32,447 of 34,534 OODS field values (93.96%) to caller main, access, arithmetic-interaction and relation-interaction trees. That census identifies where openings concentrate; it does not establish that 93.96% of runtime is spent there. The same workload has only one caller window, so cross-window batching cannot improve that fixture by eliminating repeated caller inventories. A separate narrower arithmetic layout remains necessary for that case.

## Existing authority that must survive

- `prover/block_v7_caller_active_source_v1.zig:17` binds each caller pin to one execution index, the exact native entry identity, the local-clock frame, original arithmetic key and first roots. Its epoch suffix draws arithmetic relations for that particular entry.
- `prover/block_v5_caller_fused_schedule_v1.zig:29` independently derives program/state, table and memory projection slots from the admitted statement. The memory descriptors carry the window's frame. Their offsets are not producer-supplied authority.
- `prover/block_v5_precompile_state_request_source_v1.zig:18` derives PC/clock consumption and retirement from actual committed caller rows. `block_execution_external_trace_v2.zig:163` derives the global memory base clock from the public frame; Keccak uses its actual current/+27 state rows.
- `prover/block_v7_execution_claim_closure_v1.zig:47` retains state and register residuals per native window and rejects duplicate callers. `finish` checks each window separately before closing global ROM, table, RAM and census relations. Replacing this with one untagged aggregate would lose existing isolation.
- `prover/block_v7_caller_active_layout_v1.zig:24` removes absent Keccak/recovery families but retains the byte provider and SHA inventory. Merely concatenating committed trees retains all these widths and all opening points.

## Recommended design: narrow window controls plus shared arithmetic

Keep a narrow control component for each admitted caller window. Its committed rows contain the operation kind, original PC/local clock, register and memory arguments, input/output values, and exact call identity. Its constraints continue to account for that window's original state/register retirement, decoded-ROM fetch and global-memory events. The independent window roster and per-window residual checks remain intact.

Move the wide SHA, Keccak and recovery computation rows into one bounded batch per operation family. Stack complete operations as rows in the same original arithmetic column layout, with independently derived active ranges and transition boundaries. Share fixed tables within that batch. This changes physical layout and commitment identity; it must use an explicit new protocol, not reinterpret existing active-caller roots.

A typed operation relation links each narrow control call to its arithmetic computation. Its tuple includes an admitted owner-window tag, operation ordinal and kind, arguments, and the exact input/output words or an independently constrained commitment to them. The control produces a request once; the arithmetic consumes it once. Both sides must derive these tuples from constrained committed columns. A host-generated list or precomputed success hash is not an authority. If a digest replaces full words, the digest computation itself must be proved and its cost included.

The arithmetic transition selectors must prevent one operation from falling into the next. In particular, Keccak's current/+27 link must remain within one admitted operation, and recovery's per-call table identity, scalar bounds and range checks must survive unchanged. Padding contributes zero requests and cannot satisfy an active operation. Mixed operation families remain separately tagged; one family's surplus cannot cancel another's missing request.

Use an explicit operation-provider entry or batch family in the shared epoch. Preserve independently admitted control-window entries and bind the entire source roster, batch ranges, total call counts, geometry and first roots before drawing shared operation challenges. The new control path exports an open, typed operation residual, which the final closure cancels against the shared arithmetic provider. It must not reuse the old `internal_residual == 0` receipt as if the arithmetic were still local. Absence is exact: no calls means no provider of that kind, rather than an empty dummy leaf.

## Finite implementation sequence

1. Split pure control and pure arithmetic descriptors in a new experimental module. Keep the qualified active-caller path as the oracle. Reuse the original arithmetic equations and exact lookup tuple builders; list every ownership-dependent constant before lifting any of them into columns.
2. Implement one SHA family across two actual caller windows first. Use independently admitted row ranges and one small owner/ordinal table. Prove the narrow controls, shared SHA arithmetic and all existing native/global providers in a single original STARK. Compare each original per-window state/register/ROM/RAM result, not only their total.
3. Add Keccak with explicit operation-boundary and +27-row tests; add recovery only after its per-call table and scalar rules are carried through. Reuse table providers globally rather than copying them per caller batch.
4. Measure committed cells, sampled OODS values, queried values, retained PCS, setup, interaction generation, composition, openings, verification and peak memory. Vary callers per native window and total operations independently. Compare total row counts and power-of-two padding against the current separate inventories.
5. Bound a batch by actual component rows and retained PCS bytes. A complete job that exceeds one group still needs authenticated open batch reductions and final global closure. A collection of successful batch proofs is not itself a complete execution root.

## Required negative cases

Move a call to another owner while keeping all arithmetic values valid; swap two call ordinals; omit or duplicate one request; keep total counts equal while moving counts between families; alter local-to-global clock conversion; reuse an arithmetic result for two requests; connect a Keccak final state to the next operation; substitute another recovery call's table identity; activate padding; change arguments while retaining the output; alter a typed physical claim with a compensating claim elsewhere. Every case must fail after all original producer owners have been destroyed.

## Expected benefit and limits

For many windows containing the same operation family, column width and opening count can approach one family inventory per bounded batch rather than one inventory per window. Trace height grows with the total operation count, so arithmetic work is not eliminated. Padding and fixed-table duplication may fall, while lookup/control bookkeeping grows. The benefit cannot be extrapolated as an end-to-end speedup without measurement.

The actual cut-2 fixture already supplies a useful authority oracle: ten native windows, two distinct active caller inventories, fifteen original proofs, and one independently verified 39-tree union proof. The canonical 20,495-cycle fixture has only one caller and is a useful regression, not a batching speedup benchmark. These cases and exact qualification hashes are recorded in `v7-multi-union-proof-qualification-20261029.json`.

## Target-workload correction and ownership prototype

The retained 139,214,856-cycle Ethereum workload contains 32,835 Keccak calls, 78 recovery calls and no SHA calls (the exact schedule and geometry records under `autoresearch/notes/2026-09-24-ethereum-block-delivery`). SHA is an ownership prototype, not evidence of an Ethereum speedup. Keccak is the next performance target. The active-layout work to remove absent SHA components is independent of arithmetic batching.

The initial SHA prototype closed two public boundaries only through a global tuple sum. That established arithmetic consistency but could not establish which window owned each call. The corrected design keeps the complete original caller AIR and adds a relation-only projection of its authenticated event plan over the **same committed columns**: one program event, two state events and four register-memory events. Four physical projection claims per window are absorbed individually and the three typed totals are closed separately against the independently selected window boundary. The full typed caller still enforces address consumption/emission and range checks. No filtered typed machine or host-computed RAM gap sum replaces it.

The scoped fixture uses public original CPU/memory tuples. Even after its ownership gates pass, production integration still requires the original frame-aware global RAM bridge: equal local clocks, PCs and register tuples in different windows must not make their private memory interchangeable. The fixture is not a complete execution root.

Keccak cannot directly reuse SHA's global wire-clock parameter. `keccakf_caller.coreEvents` embeds program/state/register effects and fifty word input/output memory accesses in the paired arithmetic trace; its internal I/O relation is a separate mechanism. A shared Keccak inventory must preserve the original caller/direct constraints, operation selectors and current/+27 state linkage, while independently selecting each window's control projection and applying its original global-memory frame. The concrete next gate must include equal local clocks in distinct windows, a fully recommitted owner substitution, and per-window state/register closure with the actual native counterpart. Concatenating uncolored local-clock caller rows is insufficient.

The corrected scoped SHA gate passed all six tests on 2026-10-29, including a fully recommitted owner swap and a second attack that compensates the public projection claims but fails the original STARK. Exact binary/source/log hashes and scope limitations are recorded in `v7-sha-window-ownership-qualification-20261029.json`. Its 57.04-second full test-job time includes negative proof attempts and is not proving-service latency.

The initial Keccak source seam is now implemented in `block_v7_keccak_window_{layout,source,control}_v1.zig`. The bounded layout reconstructs owner fixed columns from window counts and the original 29-row paired-slot placement, including two operations with different owners in one slot. The source helpers apply that same selector to the original control events and memory-word pair builder, preserving x0 suppression and leaving current/+27 openings mandatory. The control component shares the original caller main columns and introduces one fixed selector plus twelve interaction columns per window; it explicitly uses degree four/split two. Focused layout, off-domain source equivalence and component-inventory gates passed. These are preparation/algebra tests, **not a shared Keccak STARK qualification**. The remaining gate must prove actual native counterparts and frame-aware global RAM, including an owner swap with identical PC/local-clock/register tuples but different RAM inputs.

## Genuine shared Keccak source closure (2026-10-29)

The next gate passed 17 tests. An actual 15-cycle RV32 guest executes two Keccak calls in four native windows. The calls have identical local clock, PC, pointer register and previous-register clock; the second consumes the first output at a different global time. One five-tree batch STARK proves the original Keccak/chi/xor constraints, separate program/state/register projections per window, 28 shared table projection components and one shared 50-word RAM bridge. All physical claims enter the transcript before either interaction commitment.

The shared RAM bridge deliberately uses the **original unselected caller active weight**, with eight fixed base-clock byte columns reconstructed from the same canonical owner placement as the control selectors. It does not duplicate 50 × 48 byte-witness columns per window and does not multiply the owner into the integer bridge's existing degree-five constraints. The fixed root is recomputed by the receiver. The new batch is explicitly the local-zero recipe; it does not inherit the legacy caller profile's recipe flag. A focused test checks the real distinction: pointer-gap event 5 is suppressed for x0, as are its register effects.

Fresh verification of the four native proofs, shared batch, ROM, compact lookup and joint RAM proofs closes the entire finite execution. The fully recommitted attack swaps the complete caller records, rebuilds all affected roots and all eight source proofs under the changed epoch, and still produces a valid shared batch proof. Complete execution verification rejects its RAM transition mismatch. Thus rejection does not depend on stale commitments or differing public control tuples. A modified physical RAM claim is separately rejected by the batch STARK.

This is a diagnostic q8/PoW0 source-closure qualification, not yet a single combined execution root or canonical-security performance result. Before fresh verification the test destroys batch/native producer owners, runner and counters; the first receipt records that other provider owners remain live until deferred teardown. Stronger all-owner destruction, proof serialization and canonical positive verification are next. The exact receipt is `v7-shared-keccak-qualification-20261029.json`. The batch's 1.516-second core proof plus 0.062-second interaction and 0.118-second interaction commitments are diagnostic values; the 12.57-second job includes both complete positive and malicious cases.

Production integration will reuse the batch's original verifier components and interaction preparations inside the heterogeneous original STARK. It must not first produce a standalone batch proof and recursively wrap it merely to fit the old caller interface. Independent batch admission and typed per-window/global closure remain mandatory in the combined receiver.

### Combined shared-Keccak execution proof qualified

The combined union passed 13 diagnostic tests and the canonical q70/PoW26 positive gate (12 passed, one intentional repeated hostile-case skip). It proves the actual 15-cycle, four-native-window, two-Keccak execution as **one STARK**. Every native, batch, ROM, lookup and RAM physical claim exactly matches the eight original proofs under the same epoch. Every producer and original proof is destroyed before the combined proof is postcard-roundtripped and independently verified. Changed physical claims and an independently changed expected output are rejected.

The hostile fixture swaps complete caller records whose PC, local clock, pointer register and prior register clock are identical but whose RAM states differ. It rebuilds the entire epoch, all eight original proofs and the combined STARK. The combined STARK reaches independent global closure and is rejected by RAM consistency. This closes the ownership ambiguity that an uncolored global caller multiset alone would leave.

Canonical combined proof: 4,480,705 bytes; proving 2.340 seconds; fresh verification 1.039 seconds; charged allocator peak 253.9 MB. These are diagnostic fixture measurements. The full qualification (original oracles, codecs and negatives included) took 14.64 seconds with 204.8 MB process maximum RSS. This is not a whole-block measurement or a matched speed comparison against the previous per-window caller architecture. That comparison and daily-harness integration remain separate next gates.
