# Circuit recursion CUDA: problem match before optimization

Task and required semantics: Produce the same circuit STARK proof and Fiat–Shamir transcript as the pinned Rust R7 flow, then aggregate PIE proofs through wrap, fold, and root. No proof-stage host reads or CPU fallback; the only download is the terminal proof envelope.

Inputs, scale, and model: The recorded circuit registry has 11 AIR components, four mixed-height trace trees, four-fold FRI, and 70 queries at the canonical configuration. The local `geometry.zig`, `resident_composition.zig`, and `resident_decommit.zig` derive exact tree, source, and opening counts. CUDA time includes launch and transfer costs; GPU memory is a hard feasibility constraint.

Constraints and structure: The transcript order, canonical sample order, plain Blake2s Merkle profile, two distinct PoW challenges, and all four committed trees are fixed. Fixed circuit topology and preprocessed columns can be prepared before proof execution. Witness values, interaction challenges, and openings are proof dependent.

Candidate matches and evidence status:

| Candidate | Relationship | Fit and risk |
| --- | --- | --- |
| Lifetime-aware offline arena packing | Exact allocation subproblem; implemented in `runtime/arena.zig` | Derived from stage lifetimes; aliases only nonoverlapping ranges. Check peak and retained proof bytes. |
| Streaming or recomputation of commitments | Time/space tradeoff, not equivalent without preserving coefficients and authentication paths | Hypothesis for later profiling; adds kernels and risks changing transcript material. |
| Host-assisted proof generation | Different computational model | Rejected: violates resident proof requirement and obscures GPU performance. |

Chosen canonical problem and mapping: Assign each resident buffer a size, alignment, and inclusive stage lifetime. Reuse offsets only for nonoverlapping lifetimes, while the terminal envelope remains live from ingress through publication. This is interval-constrained storage allocation; the existing deterministic arena planner is the implementation boundary. No new allocation algorithm is needed before measured size is known.

Complexity and limits: Planner cost is secondary to proof execution; GPU peak equals the maximum assigned arena extent, plus CUDA runtime reservations. The proof must fit H100/H200 capacity with a safety reserve. The exact crossover of recomputation versus retention is unknown until profiling.

Selected transfer and falsifier: Bind the circuit plans to one proof-owned arena, prime all immutable tables at ingress, execute the entire stage schedule, then decode and independently verify the one downloaded proof. The hypothesis is that this removes intermediate transfers and exposes the real CUDA bottlenecks. A nonzero mid-proof read, CPU fallback, invalid verifier result, or memory above the target GPU falsifies qualification.

Correctness and benchmark plan: Compare stage roots, sampled values, nonces, FRI coefficients, and decoded proof against CPU/Rust vectors; verify a genuine multi-PIE wrap→fold→root proof. Record ingress, each GPU stage, publication, total latency, peak device memory, and proof bytes for all representative PIEs before optimizing kernels. Only optimize measured dominant stages, and repeat byte/parity checks after each change.

Measured qualification (H100 SXM, `sm_90`, ReleaseFast, 1 October 2026 UTC): four R7 circuit proofs passed native verification and matched the pinned Rust `CircuitSerialize` digests. Fibonacci internal/root took 0.766/0.610 s; Blake G internal/root took 0.556/0.560 s. The resident arena was 1.465–1.466 GB. The fixed one-read terminal transport was 3.295 MB, and the device stage times summed to approximately 50–60 ms. These are single runs of standalone circuit proofs, not PIE-to-root pipeline measurements.

Updated problem match: a sub-60 ms device schedule inside a 0.59–0.74 s prove call is primarily a host orchestration and setup problem at this R7 scale. Candidate causes are repeated static preprocessed-tree commitment work, twiddle preparation, per-proof AOT module/context binding, buffer allocation, kernel launch submission, and zero-filling unused terminal capacity. The benchmark must separate these with host wall timers and repeated proofs in one process before ranking them. Cache only topology-static material; keep witness-dependent work and all proof stages resident. CUDA graphs may help the repeated launch sequence, but transcript-dependent kernel arguments and per-proof buffer addresses must remain correct. The packed four-row FRI leaf format was a correctness requirement learned from the CPU/Rust implementation and also cut FRI Merkle tree storage by four.

Next falsifiers: compare first and warmed proof latency in one process; profile host call stacks and CUDA API time, then test cached static commitments/twiddles and reusable device allocations. Run the same four R7 cases after every change. A speedup that changes any Rust digest, adds a proof-stage host read or CPU PCS call, or increases peak memory beyond the target GPU is rejected. The larger wrap/fold circuits and the complete PIE-to-root path remain unmeasured.

Complete-system update (H100 SXM 80 GB, 1 October 2026 UTC): two contiguous mainnet PIEs through Cairo CUDA, two resident circuit wraps, and a resident root fold took 32.308 s from adapted inputs. The final three root files exactly match the pinned Rust reducer. The 51.5/50.9 GB Cairo arena and 28.1 GB circuit arena are planned device extents; peak whole-device memory was not sampled. Peak host RSS was 5.044 GB. A repeat run was interrupted when the GPU host was terminated for exhausted credit, so this is one complete observation.

New measured decomposition: Cairo proof execution/decode itself is 0.467/0.476 s, while each leaf's Cairo ingress is 4.460/3.979 s, with static initialization 2.096/2.064 s. The two circuit wraps cost 6.289/6.290 s, including resident proving 2.328/2.855 s and independent verification 1.702/1.442 s. The root fold costs 9.021 s; 1.475 s is circuit construction, 3.003 s resident proving, and 1.477 s verification. The 44.5-million-variable leaf circuit and the production registry are the scale; standalone R7 Fibonacci results do not predict this cost.

Problem-match brief for the next iteration:

Task and required semantics: Minimize adapted-PIE-to-identical-root latency while every Cairo and circuit STARK remains proved on CUDA and independently verified. Inputs are a contiguous sequence of PIEs, with deterministic root bytes and a dependency edge from both leaves to their fold.

Inputs, measured scale/provenance, encoding, and computational model: two real mainnet PIEs, 70 Cairo queries, 26 PoW bits, one H100 with 80 GB, 32.308 s observed once. The output is exact, not approximate; memory must admit both Cairo and circuit arenas during the in-process verified-leaf handoff.

Constraints, promises, invariants, and exploitable structure: Cairo preprocessing and the registry's circuit topology are static across these leaves; adapted inputs, witnesses, transcript challenges, and proof openings are request-specific. A Cairo proof must verify before a wrap is published, and both wraps must exist before the root fold.

Candidate matches, relationship, and evidence status: (1) batched static-resource reuse is an exact match to amortized preprocessing; the current Cairo app already reuses a runtime/preprocessed snapshot for `--repeat`, but the pipeline launches one process per distinct PIE (sourced from code and receipts). (2) parallel leaf scheduling is a DAG scheduling problem; at the measured 51 GB Cairo arena on an 80 GB H100, concurrent independent Cairo proofs are not yet safely admissible (derived). (3) reducing FRI/commitment kernels is a GPU pass/launch problem, but no production-scale event profile yet identifies a dominant kernel (hypothesis).

Chosen canonical problem and exact variant: First implement amortized preprocessing across distinct, sequential PIE requests in one process, with authenticated Cairo arena keys and a bounded leaf-topology cache. The two Cairo arena sizes differ (51.507 versus 50.894 GB), so they may have different keys; Cairo static reuse is conditional, not a guaranteed 2.064 s saving. Both leaf wraps have the same topology key and 44,505,598 variables, so retaining their shared circuit preprocessing is directly applicable. This cannot by itself yield an order-of-magnitude whole-pipeline improvement. It is lower risk than increasing concurrency before memory admission is measured.

Project-to-canonical mapping and solution recovery: one request equals one batch item; the shared CUDA runtime, same-key preprocessed snapshot, and same-key leaf topology are retained static resources; the verified Cairo callback still emits one byte-identical leaf proof per item. The existing Cairo arena key binds geometry and lifetimes, so a changed shape invalidates its reuse. The leaf cache independently uses the authenticated circuit topology key.

Complexity/limits and prediction: topology preprocessing drops from roughly `O(k * S)` to `O(S + k * D)` for `k` same-topology leaves, where `S` is static circuit construction and `D` is dynamic witness work. Cairo preprocessing only has the same bound for same-arena-key leaves. For these two leaves, the gain is unquantified until a GPU run separates topology cache hits from Cairo arena misses. Reject the change if root bytes differ, peak memory exceeds device admission, or whole-pipeline wall time fails to improve in paired runs.

Correctness and benchmark plan: compare each leaf and all three root files against the current run and Rust, verify no CPU proving fallback or intermediate D2H, measure static/ingress time per leaf and whole-device peak, then profile host setup and CUDA events on the 28 GB circuit proofs. Open uncertainty: whether the retained Cairo arena and concurrent circuit arena leave enough physical H100 headroom for safe one-process batching; use device-memory sampling rather than planned arena sums.

Further exact match, implemented locally pending GPU timing: the circuit preprocessed Merkle root is an immutable commitment. The leaf registry already supplies its authenticated expected root and the fold canonical builder independently computes its root. The prior resident circuit path recomputed that root on the CPU once before CUDA proving and again during native verification. The source handoff now carries the expected root, and the independent verifier checks the GPU proof's committed tree-zero root against it. Standalone R7 fixtures without an expected root retain recomputation. This removes two full host commitment passes per production circuit proof without altering transcript bytes; the remaining falsifier is exact Rust root parity and measured `static_hash`/verification time on the H100.

CUDA runtime reuse design brief (implemented locally, pending GPU qualification): program family is the 44.5-million-variable leaf circuit and canonical fold/root circuits on H100/H200. The final oracle is Zig verification plus byte-identical Rust root files. The measured baseline is 2.33–3.00 s resident prove per circuit, but no timer yet isolates session creation. Transcript barriers and one-read terminal publication are unchanged. The proof arena (about 28.1 GB) is request-local and released after each proof; CUDA context, authenticated AOT modules, and session allocations are process-owned. The Cairo and circuit stages share the same process-owned runtime because the CUDA backend permits one runtime owner at a time. The roughly 51 GB prepared Cairo arena is evicted after proof publication and before the wrap callback, leaving memory headroom for the 28 GB circuit arena; that forfeits Cairo prepared-arena reuse. Each circuit proof borrows a fresh transaction via `openPreparedRetained`/`finishRetained`. The full circuit plan remains proof-specific, so no arena or graph address is cached until a measured plan identity is available. There are no new streams, CUDA graphs, or extra host/device transfers. On error, the transaction aborts its retained session and the product closes or aborts the runtime. Predicted gain is context/module startup avoided across Cairo and circuit proofs, offset by prepared-arena eviction; the net result must be measured. Reject if proof bytes, residency verdict, peak memory, or paired whole-pipeline time regress. Validate standalone fallback plus retained multi-proof path and compare phase timers and root files before deeper kernel work.

Ingress transfer census from the qualified H100 Cairo receipts: the first/second PIE sent 2.551/2.520 GB host-to-device and 2.240/2.240 GB device-to-device. The ingress stage recorded 2.452/2.415 s of elapsed stage time, versus 0.467/0.476 s for subsequent proof execution and decode. Stage elapsed time includes host-side operations, so it does not isolate PCIe throughput. The preprocessed loader streams, hashes, canonicalizes, and uploads each fixed column independently; it is the leading candidate for the approximately 2.1 s static-initialization phase, but that attribution is not yet measured. New instrumentation separates initial upload, preprocessed load, and materialization. After a new GPU run, compare a bounded reusable host image, pinned/batched transfers, and unchanged streaming against this phase split, including host RSS and whole-device peak. The artifact is roughly gigabyte scale based on ingress transfer bytes, so a full host cache must justify its memory cost; do not infer a speedup from the 2.5 GB count alone.

Local lower-bound experiment, M5 Max ReleaseFast, 1 October 2026: the deterministic `canonical` coefficient exporter produced 543,100,528 words across 161 columns (2.02 GiB, SHA-256 `4d4fda06dfa3bca19554510a158f6c50abad06a74d29c17885ed4cbb88ada34d`). A standalone harness copied `preprocessed_cache.load`'s streaming SHA-256 reader, canonical-value check and `transposeSimdBlocks` call, omitting CUDA uploads. Three warm-file-cache repetitions took 1.026, 1.010 and 1.012 s total; median breakdown was 0.695 s read/hash, 0.119 s validation and 0.197 s transpose. This is not an H100 measurement and omits upload/materialization, but it bounds the payoff from moving the transpose alone: on this host, at most about 0.2 s per PIE. A reusable authenticated host image could remove more repeated work, at about 2.02 GiB added host residency; test that trade-off only with a paired H100 run and explicit memory accounting.

Experimental transfer reuse, implemented opt-in pending GPU qualification: the exact fixed coefficient image is captured from the first proof's validated resident coefficient slice into a separate 543,100,528-word persistent CUDA buffer. Admission occurs only after independent Cairo proof verification. The batch product releases each Cairo proof arena before building its circuit wrap, but preserves this 2.17 GB image. If the next PIE's artifact path, column identities and commitment identity match, it restores coefficients by one device-to-device copy and skips the host artifact parse, SHA, canonical-value validation, transpose and host-to-device upload. A different key evicts and rebuilds the image. This is a snapshot of the first validated source, so a mutation of the source file after admission does not change the batch's fixed coefficients. The setting is `STWO_CAIRO_CUDA_STATIC_IMAGE=1` and remains off by default. Predicted benefit is approximately the repeated 1.0 s M5 preparation plus part of the H100 ingress transfer, offset by one extra device copy on the first PIE and 2.17 GB higher GPU residency. Reject if output bytes differ, the device verdict loses residency, the image leaks across runtime teardown, or the sampled peak exceeds capacity.

Cross-backend first-leaf calibration on the same reproduced adapted input (M5 Max ReleaseFast CPU/Metal; H100 CUDA is the earlier qualified run): CPU Cairo prove 31.48 s plus circuit wrap 12.07 s; Metal 18.45 s plus 11.78 s; H100 CUDA 4.984 s plus 6.289 s. Pinned Cairo proof parity, local M5, 1 October 2026: the pinned `proving@5a7c5ed` Rust oracle proved the two exact adapted PIE inputs under the production registry and returned Cairo binary SHA-256 `a699160c...9ff1` and `7304ccf3...206a` (3,346,454 and 3,345,638 bytes). The CPU recursion leaf lane produced canonical binaries with those exact SHA-256 values, and the pinned Rust Cairo verifier accepted both. The generic `stwo-cairo@82f2125` verifier rejected the lifted leaf protocol at DEEP-ALI, so it is not this profile's oracle. Investigation exposed that our shared Cairo JSON writer emitted the legacy `min_lifting_log_size: 0` header even though the leaf protocol uses the two-height PCS config at height 26. Replacing only the JSON header with `fri_config.pow_bits: 26`, `trace_lifting_log_size: 26`, and `preprocessed_lifting_log_size: 26` made both local CPU leaf proofs accepted by the pinned Rust verifier with exact Rust binary parity. The CPU and Metal leaf products now expose optional `--cairo-proof` output with this pinned header; fresh runs for both PIEs produce byte-identical JSON across CPU and Metal, and pinned Rust accepts both with exact binary parity. CUDA publication now emits that pinned config directly. This leaves transcript/proof bytes and the recursive root unchanged, but the fix remains GPU-unqualified until the next H100/H200 run retains both published CUDA JSON proofs and independently verifies their canonical binary digests. Full reference values and checkpoint hashes are in `vectors/reports/recursive-product-20260918/cuda-resident-pipeline-h100-20261001/pinned-cairo-reference.json`.

System-level speed ceiling, derived from the single qualified H100 receipt: the two Cairo execute/decode intervals total 0.943 s; the three resident circuit-prove calls total 8.186 s; the remaining 23.179 s of the 32.308 s includes ingress, circuit construction, proof verification, process/setup and publication. Even eliminating both measured prove sections entirely would yield only 1.39× total speedup. These sections include host work, so this is a generous upper bound for GPU-kernel-only tuning. The practical path to a large end-to-end gain must remove repeated setup and transfers and reduce host circuit construction/verification cost or overlap independent work without weakening the proof gate. Test this after the paired H100 batch/static-image run with phase timers; no new speedup has been measured yet.

Scheduling candidate, hypothesis pending phase data: an independently decoded child circuit proof can be verified on a CPU worker while the single-owner CUDA runtime proves the next Cairo leaf. The parent circuit construction needs the child proof bytes but does not logically need the local independent verifier's verdict until final publication; the parent circuit itself verifies its child. The two leaf circuit verification intervals total 3.144 s in the baseline, so overlap could save at most that much serial wall time before CPU contention and thread handoff costs. Keep every child verifier result as a mandatory publication gate and retain the final root verification. Do not implement until the paired batch run shows that CPU verification remains on the critical path after runtime reuse and measures the host memory cost of keeping decoded child proofs alive.

Full-pipeline CUDA design gate, 1 October 2026 (applies the repository's problem-matching, CUDA design, and CUDA profiling skills):

- **Task/semantics and canonical match:** schedule a two-branch proof DAG (Cairo PIE → verified circuit wrap for each branch, then one root fold) while minimizing verified adapted-input-to-root wall time under exact proof bytes, no CPU STARK proving, one terminal read per proof, and a finite GPU-memory budget. This is a resource-constrained DAG scheduling and amortized-static-preprocessing problem, not primarily a single-kernel throughput problem. The mapping is exact for scheduling; CUDA Graphs and memory pools are candidate implementation techniques, not equivalent algorithms.
- **Inputs and cost model:** two contiguous PIEs with 1,224,007 and 785,807 Cairo steps; H100 SXM 80 GB; 32.308 s observed once. The measured sequential branches are 11.272 and 10.801 s, with a 9.021 s root and 1.214 s process overhead. On this one run the 9.129 s of Cairo execute/decode plus resident circuit-prover calls is only 28.3% of the wall time. A tenfold reduction of these calls alone would leave approximately 24.092 s (1.34× total speedup), a **derived bound**, even before any new overhead.
- **Resource/lifetime table:** Cairo's prepared arena occupies up to 51,506,694,880 planned bytes from ingress through its terminal proof. Circuit wrap/root arenas occupy about 28.1 billion planned bytes each, one circuit proof at a time. The optional fixed-coefficient image persists across leaf requests at 2,172,402,112 bytes. Cairo's terminal read is 8,994,704 bytes and each circuit proof's terminal read is 4,018,944 bytes. The first two arenas sum to about 79.6 billion planned bytes before CUDA runtime, scratch, image, and allocator reservations; retaining both on the qualified 80 GB H100 is therefore not admitted. H200 capacity makes overlap plausible but not proven beneficial: memory fit alone says nothing about SM or bandwidth saturation. Host RSS peaked at 5.044 GB in the prior separate-process run; the batch peak is unmeasured.
- **Proof-program dependencies and cache identity:** transcript absorbs/challenge draws and successive FRI rounds are hard barriers. The Cairo combined-arena key binds its plan and resident controller identity; the fixed image additionally binds artifact path, fixed-column identities, and preprocessed commitment identity. The circuit leaf cache binds the authenticated topology; the registry or canonical fold supplies the expected preprocessed root, and the verifier still checks the GPU commitment. Witness, interaction challenges, openings, and terminal proof bytes remain request-local. A cache miss or teardown must not leave a dangling device allocation.
- **Pass and transfer ledger:** each Cairo request sends 2.52–2.55 GB host-to-device, moves about 2.24 GB device-to-device during ingress, and has roughly 4.0–4.5 s of ingress versus 0.47 s execute/decode. The fixed-coefficient image specifically removes repeated artifact parsing/hashing and fixed-table H2D upload while adding one first-request capture copy and one restore copy per matching request. Exact device-stage and host-phase deltas require the next run; the M5 1.01 s local parser/hash/transpose timing is not a GPU speedup claim.
- **Alternatives and external mechanism evidence:** CUDA Graphs can reduce repeated launch submission when graph topology and parameters are stable, and NVIDIA documents in-place parameter updates for that case ([CUDA Graphs guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html), **sourced**). Here graph capture spans cannot cross transcript-dependent host barriers without redesign, the proof arenas currently change, and even eliminating all measured prover-call time has the 1.39× bound above; graphs rank below ingress and host reuse until an Nsight timeline identifies launch gaps. NVIDIA's stream-ordered allocator can reuse freed memory when stream dependencies permit ([CUDA allocator guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/stream-ordered-memory-allocation.html), **sourced**), but the current proof already packs its large buffers into one lifetime-aware arena, so an allocator switch has no demonstrated end-to-end benefit. Kernel tuning and two concurrent leaves are deferred until event/occupancy and memory measurements justify them.
- **Selected transfer and integration boundary:** compare serial, shared-runtime batch, and batch plus opt-in fixed-coefficient image on the same GPU/binary in ABCCBA order using `run_cuda_resident_paired.sh`. Each run checks exact input, leaf, security, and root digests against the Rust-qualified receipt, proves on CUDA without fallback, and samples whole-device memory. Retain both Cairo JSON files and run the pinned Rust verifier outside the timed boundary. The next profiler is Nsight Systems on the dominant surviving host/device gap, then Nsight Compute only if a kernel owns material critical-path time.
- **Prediction, falsifier, and open uncertainty:** shared runtime should reduce cold startup and repeated leaf topology work; the image may reduce the second PIE's static phase, but its first-request copy and 2.17 GB residency may erase the gain. Keep an optimization only if repeated median adapted-input-to-root latency falls, all exact parity gates pass, and sampled peak fits the target GPU with headroom. The missing H100 paired result, the first whole-device peak, and a CUDA Cairo JSON checked by pinned Rust remain the decisive unknowns. No ABCCBA result has been measured yet because RunPod credit was exhausted.
