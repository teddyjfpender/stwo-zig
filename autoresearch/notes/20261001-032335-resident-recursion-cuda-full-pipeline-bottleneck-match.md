Full-pipeline CUDA design gate, 1 October 2026 (applies the repository's problem-matching, CUDA design, and CUDA profiling skills):

- **Task/semantics and canonical match:** schedule a two-branch proof DAG (Cairo PIE → verified circuit wrap for each branch, then one root fold) while minimizing verified adapted-input-to-root wall time under exact proof bytes, no CPU STARK proving, one terminal read per proof, and a finite GPU-memory budget. This is a resource-constrained DAG scheduling and amortized-static-preprocessing problem, not primarily a single-kernel throughput problem. The mapping is exact for scheduling; CUDA Graphs and memory pools are candidate implementation techniques, not equivalent algorithms.
- **Inputs and cost model:** two contiguous PIEs with 1,224,007 and 785,807 Cairo steps; H100 SXM 80 GB; 32.308 s observed once. The measured sequential branches are 11.272 and 10.801 s, with a 9.021 s root and 1.214 s process overhead. On this one run the 9.129 s of Cairo execute/decode plus resident circuit-prover calls is only 28.3% of the wall time. A tenfold reduction of these calls alone would leave approximately 24.092 s (1.34× total speedup), a **derived bound**, even before any new overhead.
- **Resource/lifetime table:** Cairo's prepared arena occupies up to 51,506,694,880 planned bytes from ingress through its terminal proof. Circuit wrap/root arenas occupy about 28.1 billion planned bytes each, one circuit proof at a time. The optional fixed-coefficient image persists across leaf requests at 2,172,402,112 bytes. Cairo's terminal read is 8,994,704 bytes and each circuit proof's terminal read is 4,018,944 bytes. The first two arenas sum to about 79.6 billion planned bytes before CUDA runtime, scratch, image, and allocator reservations; retaining both on the qualified 80 GB H100 is therefore not admitted. H200 capacity makes overlap plausible but not proven beneficial: memory fit alone says nothing about SM or bandwidth saturation. Host RSS peaked at 5.044 GB in the prior separate-process run; the batch peak is unmeasured.
- **Proof-program dependencies and cache identity:** transcript absorbs/challenge draws and successive FRI rounds are hard barriers. The Cairo combined-arena key binds its plan and resident controller identity; the fixed image additionally binds artifact path, fixed-column identities, and preprocessed commitment identity. The circuit leaf cache binds the authenticated topology; the registry or canonical fold supplies the expected preprocessed root, and the verifier still checks the GPU commitment. Witness, interaction challenges, openings, and terminal proof bytes remain request-local. A cache miss or teardown must not leave a dangling device allocation.
- **Pass and transfer ledger:** each Cairo request sends 2.52–2.55 GB host-to-device, moves about 2.24 GB device-to-device during ingress, and has roughly 4.0–4.5 s of ingress versus 0.47 s execute/decode. The fixed-coefficient image specifically removes repeated artifact parsing/hashing and fixed-table H2D upload while adding one first-request capture copy and one restore copy per matching request. Exact device-stage and host-phase deltas require the next run; the M5 1.01 s local parser/hash/transpose timing is not a GPU speedup claim.
- **Alternatives and external mechanism evidence:** CUDA Graphs can reduce repeated launch submission when graph topology and parameters are stable, and NVIDIA documents in-place parameter updates for that case ([CUDA Graphs guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html), **sourced**). Here graph capture spans cannot cross transcript-dependent host barriers without redesign, the proof arenas currently change, and even eliminating all measured prover-call time has the 1.39× bound above; graphs rank below ingress and host reuse until an Nsight timeline identifies launch gaps. NVIDIA's stream-ordered allocator can reuse freed memory when stream dependencies permit ([CUDA allocator guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/stream-ordered-memory-allocation.html), **sourced**), but the current proof already packs its large buffers into one lifetime-aware arena, so an allocator switch has no demonstrated end-to-end benefit. Kernel tuning and two concurrent leaves are deferred until event/occupancy and memory measurements justify them.
- **Selected transfer and integration boundary:** compare serial, shared-runtime batch, and batch plus opt-in fixed-coefficient image on the same GPU/binary in ABCCBA order using `run_cuda_resident_paired.sh`. Every run checks exact input, leaf, security, and root digests against the Rust-qualified receipt and proves on CUDA without fallback. Three separate memory trials sample whole-device usage; the ABCCBA timing trials run without the sampler. Retain both Cairo JSON files and run the pinned Rust verifier outside the timed boundary. The next profiler is Nsight Systems on the dominant surviving host/device gap, then Nsight Compute only if a kernel owns material critical-path time.
- **Prediction, falsifier, and open uncertainty:** shared runtime should reduce cold startup and repeated leaf topology work; the image may reduce the second PIE's static phase, but its first-request copy and 2.17 GB residency may erase the gain. Keep an optimization only if repeated median adapted-input-to-root latency falls, all exact parity gates pass, and sampled peak fits the target GPU with headroom. The missing H100 paired result, the first whole-device peak, and a CUDA Cairo JSON checked by pinned Rust remain the decisive unknowns. No ABCCBA result has been measured yet because RunPod credit was exhausted.
