# Exact-count V2 single recursive root (2026-09-25)

`zig build test-blake3-exact-root -Doptimize=ReleaseFast` passed a fresh CPU verification of **one outer proof for six real execution segments**. The admitted child forest consisted of a four-segment dyadic proof and a two-segment dyadic proof. The outer STARK includes both child verifiers in one joined, namespace-separated row roster. It does not prove padded execution leaves or create invalid intermediate prefix `SpanStatement`s. The receiver derives the complete root statement from the independently supplied `JobContext`.

All child and outer keys used the BLAKE3 execution-parent `csp_q70_pow26` profile (70 FRI queries, 26 PoW bits). The single outer postcard artifact was **975,788 bytes** and passed fresh decode/verification. The test rejected a changed independently supplied forest-roster digest before proof decoding. Its tracked peak allocation was **8,327,660,189 bytes (7.76 GiB)** for the whole six-segment proof chain, including retained child captures. This is a small guest fixture and is not an Ethereum block timing.

The three two-segment parent proofs took 40.20, 40.50, and 40.26 seconds in their recorded proof/check phases; the four-segment parent took 59.54 seconds. The whole test took roughly five minutes. The outer 4+2 stage was not separately timed, so there is no qualified standalone outer-prove or verify latency yet.

The V2 exact-root key extension binds the ordered forest-roster digest, every child verifier context identity, each disjoint namespace plan, and the receiver-derived root statement identity. The extension is absent from existing v3 parent keys, preserving their identities. The detached receiver API `exact_root.verifyBytes` requires an **independently pinned outer `Admission` key ID** and an independently pinned forest-roster digest; it checks the exact child count, key binding, expected root statement, and fresh PCS proof. A bundle must not self-authorize its outer key. The existing V2 forest receiver remains a valid independent multi-proof path while producer/receiver transport for this one-root artifact is integrated.

This test uses the existing custody-bearing execution leaves. The block-v3 custody-free execution leaf wrapper and the block memory/source global relation closure are separate integration gates before claiming an end-to-end one-root Ethereum block proof. The private RW initial source has its own [qualification](rw-initial-joint-v2.md); mainnet currently uses the verifier-visible initial image fallback.
