# RTX PRO 6000 Blackwell: two memory/proving rounds

This experiment used one RTX PRO 6000 Blackwell Server Edition (97,887 MiB reported VRAM, 188 SMs, CUDA 12.8, driver 595.91.07) and a host with 2 TiB RAM. The source base was `6692d40639c88becff2a203c45727f31cbe23ad3`; the changes in this branch are the candidate. The registry is `vectors/circuit/official/registries/production.json` (70 queries, 26 PoW bits). The three real one-block PIEs are from the saved contiguous settlement campaign, not synthetic circuits. Their input hashes and transaction/step/builtin counts are in [cases.csv](cases.csv). The immutable preprocessed coefficient file had SHA-256 `4d4fda06dfa3bca19554510a158f6c50abad06a74d29c17885ed4cbb88ada34d`.

Round 1 established the production-registry baseline, admitted bounded managed-memory oversubscription behind `STWO_CUDA_MANAGED_OVERSUBSCRIBE=1`, and made the singleton leaf-wrap handoff retire the Cairo arena before allocating the circuit arena. It also fixed SM 120 admission for the combined Cairo/circuit executable. Normal device allocation remains the default. Round 2 added explicit proof-stage prefetches behind `STWO_CUDA_MANAGED_PREFETCH=1`; these move the lookup slab and main coefficients across their idle phases, preserve the transcript, and account for the extra synchronization in residency telemetry. This turned the hardest PIE from a 162.7-second uncompleted managed-memory attempt into a completed, verified Cairo proof and leaf wrap. A distinct-input batch then exposed a pool/managed-memory interaction, so round 2 also corrected pool reuse for fitting arenas and trims unused pool pages before an oversized managed arena.

Every candidate leaf's `circuit_preprocessed_root`, `circuit_hash`, and entire proof field matched the saved H200 settlement leaf object byte for byte, including the repeated saturated run. The CUDA circuit prover also ran its independent verifier before publication. The repeat's extra 9.42 seconds came almost entirely from fixed-asset loading: the static ingress subphase increased from 0.659 to 10.222 seconds, while GPU proof/decode stayed at 21.28–21.38 seconds. These are single commands, not statistical latency distributions. The 200 ms `nvidia-smi` sampler can miss brief peaks; its 97,249 MiB peak left only 4 MiB of reported free memory in the two oversubscribed cases. This proves feasibility on this host, not reliable capacity under co-tenancy or on a lower-RAM machine.

The standard top-level `circuit-recursion-cuda-resident` build passed with `-Dcuda-arch=sm_120`. Its independent binary reproduced the earlier fitting leaf, saturated leaf, and two-leaf root proof **byte for byte**; [build_and_parity.json](build_and_parity.json) records its binary and proof hashes. The top-level saturated leaf command took 29.18 seconds at the same 97,249 MiB sampled peak. This matters because the earlier exploratory proofs used a staged native archive while the standard product was being rebuilt.

The batch A/B used two **distinct** PIEs in one runtime, fitting `16309292_16309292` followed by managed `16309286_16309286`; both leaf proofs stayed byte-identical to the H200 references. The second wrap was a genuine topology-cache hit in every run.

The like-for-like image-on change is **2.96× faster** end to end. It removes a mistaken managed placement for the 28 GB wrap and returns unused retained pool pages before the next oversized Cairo proof. The old `cudaMemGetInfo`-only decision omitted the reusable bytes held by the process's async pool; the pool's release threshold is deliberately maximal. NVIDIA's [stream-ordered allocator documentation](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__MEMORY__POOLS.html) defines the distinction between pool-reserved and pool-used bytes and the explicit trim operation. The image-off run is a useful memory tradeoff, but its 10.76-second lower full-command time cannot all be attributed to the image setting: first-PIE ingress varied from 11.85 seconds in the image-on run to 2.13 seconds in the image-off run. The second proof/decode improved by 1.05 seconds with the image off, while static work rose by about 0.54 seconds. More repeated idle-host runs are required before changing the default for all batches. [batch_comparison.csv](batch_comparison.csv) retains all per-leaf timings.

The saturated proof issued four explicit prefetches, covering 48.17 GB of requested hostward ranges and 48.17 GB of requested deviceward ranges; these counters are requested bytes, not measured PCIe traffic. Its GPU stage times were 4.15 s trace generation, 6.57 s trace commitment, 4.14 s constraint evaluation, 4.27 s quotient, and 1.85 s decommitment. The corresponding fitting-PIE stages were 0.134, 0.530, 0.211, 0.069, and 0.014 s. Managed paging is therefore a capacity rescue with a large proving-time penalty, not a performance win. The [stage CSV](cairo_stage_times.csv) retains all ten stages and migration counters; the original per-trial receipts and sampled memory traces are in `raw-receipts.tar.gz`.

For context, the earlier H200 settlement campaign recorded 1.342, 1.462, and 1.760 seconds of Cairo proving for the fitting, near-limit, and saturated PIEs respectively, with 7.746, 7.863, and 8.239 second proof commands. Those are saved campaign measurements from a different host and execution path, not a controlled A/B against this CLI. The exact proof parity makes their workload identity useful, but the RTX managed-memory path is plainly much slower on the saturated case.

The circuit arena was 28.13 GB per fold and 28.12 GB for a leaf wrap. Per-pair fold circuit construction was about 205 ms, while cached later resident proofs were about 334–349 ms; their `finish` phase alone was about 246–261 ms. This round did not make fold arithmetic faster. It qualified the Blackwell backend, confirmed that one retained arena bounds VRAM across 15 reductions, and identified circuit value construction and the terminal synchronization as the next fold speed targets. The singleton wrap now uses the same lifecycle as the batch path; this prevents a Cairo/wrap arena overlap on a 96 GB card. A leaf wrap still costs about 1.4–1.6 seconds, of which the resident circuit proof is about 0.36–0.60 seconds. Topology/value construction and arena retirement are the remaining wall-time costs.

The historical settlement file contains 41 one-block PIEs. Two had planned Cairo arenas above 100 GB; the largest is the 118.89 GB case proved here. One further case is 97.92 GB planned and was **not** run on this card. The strict-allocation pass/fail boundary was observed between 93.94 and 103.12 GB planned, with 97,252 MiB free before each command. All 41 were not re-proved, so this is an observed three-point boundary, not a claim that every other PIE fits. A planned arena alone is not a reliable admission limit under managed memory: the 118.89 GB plan ran with a nearly full 96 GB GPU and a large 2 TiB host, at 21.3 seconds of proof/decode. A production capacity rule needs a physical-headroom margin and repeated distinct-input runs.

The next architectural experiment should reduce live bytes, not merely move them to host. The saturated lookup slot is 31.87 GB, versus 25.24 GB in the fitting case; long-lived commitment/coefficient slots occupy much of the remainder. A bounded streamed lookup/commitment design should generate or transfer tiles only for the current phase and prove that no later verifier opening reads a discarded tile. CUDA virtual-memory remapping could preserve stable addresses while backing nonoverlapping phases with the same physical allocation, but the present planner already aliases many nonoverlapping slots; a phase-by-phase live-set audit must establish additional savings before implementation. NVIDIA's [Unified Memory guidance](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html) describes oversubscription and prefetch behavior, and its [VMM guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/virtual-memory-management.html) documents explicit virtual/physical mapping. A CUDA DSL such as Triton/Gluon may help an individually profiled AIR or commitment kernel, but it will not remove the measured 103–119 GB live-set pressure or fixed-asset ingress. Kernel rewrites should follow a GPU timeline on a fitting case, with proof parity and peak VRAM as acceptance gates.

`run_metrics.csv` is the compact singleton/fold run index; `cases.csv` contains workload descriptors, `cairo_stage_times.csv` contains CUDA stage data, [fold_pairs.csv](fold_pairs.csv) breaks out all 26 measured pair reductions, [proof_checks.csv](proof_checks.csv) records proof-field hashes and exact H200 comparisons, and [raw-receipts.tar.gz](raw-receipts.tar.gz) contains the full `.json`, `.report`, `.log`, and `.samples.csv` receipts. The proof objects are deliberately omitted from Git; comparisons used the saved settlement leaf inputs. To reproduce on a CUDA 12.8/SM 120 host, build the resident CLI with `-Dcuda-arch=sm_120`, set `STWO_CAIRO_CUDA_PREPROCESSED_COEFFICIENTS` to the immutable coefficient file, and run [the measurement harness](../../experiments/rtx6000-pro/measure.py) around `stwo-circuit-recursion-cuda leaf-wrap`, `leaf-wrap-batch`, or `fold-tree`. Set both managed-memory flags only for an explicitly admitted oversubscription experiment; leave them unset for the ordinary capacity and speed baseline.
