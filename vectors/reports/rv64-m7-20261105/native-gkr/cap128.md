# M7 CUDA GKR capacity gate

The saved `3d5ace6d7` capacity-only patch built successfully on the two-RTX-5090
pod with `TMPDIR=/workspace/m3/tmp`. The resident-image link and stack admission
passed. The M6 device-link segfault did not recur; disk exhaustion remains a
plausible historical cause, not a proven diagnosis.

Measured [M], six resident requests (three rounds, both dev blocks): every native
proof bin, bundle, recursive node proof and tree is byte-identical to the M6
default `c1-bench` receipts. Separate cache-disabled, GPU-disabled receivers
accepted both blocks with the artifact store absent. The daemon's built-in
M3 comparison is intentionally false because M6 changed the outer format;
`cap128-m6-parity.json` is the explicit M6 comparison.

Warm single observations [M], on a loaded pod (load average approximately 15):

| block | request seconds | native seconds | root bytes |
|---|---:|---:|---:|
| 26235156 | 13.107 / 13.463 | 3.140 / 3.305 | 750,136 |
| 24628607 | 18.797 / 18.154 | 4.559 / 4.454 | 708,696 |

The change raises a capacity limit. These observations establish compatibility,
not a speed improvement. Native `v2-gkr` is still refused by the production
selector: removing classic interaction columns and binding GKR roots through
the native AIR, GPU projection, leaf verifier and receiver are separate work.

Reproduce the explicit parity gate with `scripts/rv64_m7_native_parity.py`,
passing the recorded daemon directory and `/workspace/m3/runs/m6-integrate`
as `--references`. Build and run identities are retained in `cap128-build.json`
and `cap128-daemon.json`.

Capacity stress test [M]: native reference fixtures at 65 and 128 oracles pass
the GPU mixed-height sumcheck gate (17 cases plus 5 poison cases). This tests
the expanded by-value packets and state offsets beyond the previous limit.
See `cap128-capacity.json` and its log.
