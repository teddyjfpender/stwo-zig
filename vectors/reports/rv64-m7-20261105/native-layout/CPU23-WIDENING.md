# CPU23/24 source extension and fewer-leaf admission

Status: design [E], checked against current receiver-owned source. No new class or rung is admitted by this document.

Current CPU log23 is already a classic wide-clock class. `word16_execution/layout.zig` caps log23 and switches after log22: REG time is `4*row+slot+1`, while OWNER/RAM time becomes `row+1`. Three gap-high limbs are less than 512 and are checked as U16(128*gapHigh), replacing the three U8 checks. The source constructor admits this only with fused-tail and without byte pairs. Compact decode is currently conditional on byte pairs, so relaxing only the maximum log would select invalid equations and lookup multiplicities. Current compact MAIN37 and wide MAIN47 are distinct supported structures.

A CPU23 compact extension must introduce a separately authenticated source mode. It can retain the compact decode/operand columns while using the wide-clock gap queries. The proposed clock tail replaces the two CPU byte-pair queries with three scaled U16 queries; all unrelated MUL/LS pair users retain their own table columns and multiplicities. The exact emitted source term count must be recomputed from this mode, not copied from the current compact class. The source mass authority must move the three CPU gap terms from the pair/AND relation to range16. Prover, GPU projector, CPU receiver, typed leaf and Tnat must derive the same mode and term order from the source class.

For CPU24, REG time can reach almost 2^26, so the gap-high limb requires ten bits. A new scale64 U16 check bounds it below1024; reusing scale128 would reject honest traces. OWNER/RAM tick `row+1` remains below2^24 for active rows because steps is strictly less than the row capacity. Public register clocks remain bounded by4*steps and need nonwrapping integer constraints, alongside x0, PC alignment and compact-PC injectivity. Both CPU23 compact and CPU24 require fresh source geometry flags, layout identity, FIXED root, full PCS structure hash, local/global query census, signed mass caps, conditional degree bounds and receiver profile identity. Native-GKR service scope, GPU codegen public projection, typed CPU policy and class caps currently stop at22 and must change together. Old classes and proof domains must remain frozen.

Suggested cheap gates before any full request: source-generated tuple/census differential across classic-wide and proposed compact-wide at tiny rows; exact clock endpoints at2^24,2^25 and2^26 without allocating those traces; high-gap511/512 and1023/1024 negatives; compact state/PC and family-policy negatives; native CPU proof/fresh receiver plus numerical GKR/circuit transcript equivalence; then actual recursive graph cell census. A class must remain unavailable if any old scope rejects it. Memory admission must precede any large GPU trial.

The existing exact model gives CPU23+truth1 seven/nine physical proofs on the two dev blocks, but nine/twelve outer nodes. CPU24+truth1 reaches eight/nine outer nodes but is currently source-invalid and exceeds22GiB with full-tree GKR. Another route keeps CPU23 physical proofs and verifies two CPU proofs in one typed recursion leaf: the headline would have seven leaves and nine total outer nodes. Its verifier graph/cell/memory cost must be measured before selection. Merging all Keccak proofs is itself memory-negative under the current runtime: its workspace alone is19,541,918,976 bytes, excluding4,169,138,176 decoded-source bytes and retained MAIN. Streamed GKR and one global planner are structural prerequisites; count reduction alone does not establish a speed gain.
