# Starknet OS PIE size and CUDA-proof study, 1 October 2026

The [full joined CSV](pie-scale.csv) has one row per ready mainnet PIE from a
single catalogue pass against the [Lord of the Pies API](https://15-237-92-219.sslip.io/v1/docs).
The [source-metadata CSV](pie-catalog.csv) contains **6,187 ready PIEs** and
31 metadata columns. These include Cairo OS steps, memory holes, builtin
counts, archive size, block range, and the service's SNOS *baking* timings.
The `bake_*` fields are **not** our prover's timings. All 6,187 metadata rows
report `header_matches_chain=True`; the API's check is an OS-output-header
check against mainnet, rather than a proof generated by this repository.

The joined CSV adds adaptation and CUDA proof columns by exact PIE name.
Blank measurement cells mean that PIE was **not measured**, not that the time
or memory was zero. The cohort was chosen near 1M, 2M, 4M, 6M, 8M, 10M, 12M,
14M, 16M, 18M, 20M, 24M, 28M, 32M, and 40M steps, plus the requested
`15553620_15553629` at 179.94M steps for admission analysis. All 16 archives
and their API metadata were downloaded with
[fetch_starknet_pies.py](../../../../scripts/fetch_starknet_pies.py) and adapted
for the 15 smaller PIEs with the pinned Rust leaf bootloader using
[adapt_starknet_pie_cohort.py](../../../../scripts/adapt_starknet_pie_cohort.py).
Every adapted file was hashed before transfer and checked again on the H200.

The 179,936,666-step PIE `15553620_15553629` is a legacy ten-block range,
not representative of the newer ~30M-step sizing policy. Its archive is
953,263,717 bytes and its metadata reports 18,537,302 memory holes. The
current CUDA product rejects adapted files above 2 GiB. The 40M-step cohort
input is already 771 MB, so the 180M case needs an explicit size and memory
admission decision; a linear estimate is not a measured adapted size or proof
footprint. Re-baking that old block range into new contiguous PIE boundaries
would change the workload and requires a separately qualified chain.

The 15 local Rust adaptations from 0.986M to 39.941M steps took **0.681–12.446
s** each and peaked at **0.476–12.868 GB host RSS**. Their compact inputs range
from **26.8–771.3 MB**. These are bootloader execution and adaptation costs,
outside the adapted-input-to-proof CUDA timing. The [adaptation receipt](adaptation.csv)
records each PIE separately.

CUDA proving uses [benchmark_cairo_cuda_pie_cohort.py](../../../../scripts/benchmark_cairo_cuda_pie_cohort.py)
with canonical 70-query/26-bit query PoW and 24-bit interaction PoW security,
one PIE per process, and whole-GPU memory sampled through NVML. The H200 and
protocol are recorded in [h200-machine.json](h200-machine.json). Of the **15**
adapted inputs, **14 produced canonical proofs accepted by the pinned official
Rust verifier**. The [individual proof receipts](pie-proving.csv) and [full
joined catalogue](pie-scale.csv) contain the raw measured columns; the Rust
verifier binary and pinned source revisions are recorded in
[verifier-machine.json](verifier-machine.json). All bytes below are decimal GB.

`Adapt M5` is the local Rust leaf-bootloader adaptation wall time and includes
reading the already downloaded PIE archive. `Source` is the H200 adapted-input
source stage, including parsing and planning, so it is not a pure disk-read
measurement. `Fixed load` is loading and uploading the canonical 2.1 GB
preprocessed coefficient asset. `Other ingress` includes runtime setup,
uploads, controller and writer preparation, and transcript binding. These
three columns sum to H200 ingress. `Proof` times resident proof execution and
finish; the backend's legacy JSON key says `proof_execute_and_decode_ns`, but
its timer actually stops **before** host canonical verification and decode.
`Publish` includes that host verification/decode and proof serialization.
The four H200 components sum to `Input→proof`, the already-adapted input to
published proof latency. `Verify M5` separately times the official Rust
verifier process; `proof_rust_verify_inner_s` in the CSV excludes process
startup. All phase columns and their finer ingress subphases are in the CSV.
Network download and queueing were **not timed**. The Mac adaptation and
verification times and the H200 proving times are distinct machine-stage
measurements, not one measured end-to-end wall time.

For the 20.003M-step PIE, the H200's **7.028 s** to publication splits into
1.916 s source preparation, 2.365 s fixed-asset load, 1.521 s other ingress,
1.156 s proof execution/finish, and 0.070 s host verification/serialization.
The separate Rust verifier took 0.058 s wall time (0.037 s inside the verifier).
The Rust adaptation took 6.277 s on the M5. Its peaks were **98.8 GB GPU**
and **1.80 GB H200 host RSS** during proving, and **6.68 GB M5 host RSS**
during adaptation. The first 0.986M-step trial paid a cold 4.847 s fixed-load
cost; subsequent trials took 2.365–2.563 s for that stage. Therefore even
the 0.385–1.423 s proof kernel/finish times are not the publication latencies:
ingress is currently dominant for these PIEs.

The 39.941M-step PIE **did not produce a proof**. It failed in
`prepare_controllers` with `TraceCommitGeometryOverflow`, after 4.210 s of
process time and before significant GPU allocation. The failure is a geometry
admission issue, not an observed GPU OOM; the exact overflowing expression
needs a diagnostic. The current geometry stores column offsets as `u32`.
At 27.952M steps, sampled H200 device usage already reached 133.7 GB; at
31.906M it was 125.8 GB. This non-monotonicity means step count alone cannot
predict memory: component mix and trace geometry matter. The new variable-size
PIE policy tops out at 35.605M steps in this catalogue, but the old fixed-size
history contains much larger PIEs. Their admission and memory use remain
unmeasured. The user-requested 179.94M-step PIE was downloaded and catalogued,
but was not adapted or proved; it would be incorrect to extrapolate a time or
memory number for it from this cohort.

The GPU peak is sampled whole-device usage, a lower bound on an instantaneous
peak, while H200 prover host RSS and M5 adaptation RSS are process peaks in the
CSV. Each PIE has one H200 trial, so these are sizing observations rather than
latency distributions. The fixed preprocessed asset is loaded in every
one-PIE process; persistent batching could amortize it but was not part of
this benchmark.

Exported proofs were checked with
[verify_cairo_cuda_pie_cohort.py](../../../../scripts/verify_cairo_cuda_pie_cohort.py).
The joined CSV contains all **6,187** unique PIEs and 69 columns, with blanks
for unmeasured stages. The [catalogue tool](../../../../scripts/catalog_starknet_pies.py)
and [join tool](../../../../scripts/join_starknet_pie_scale.py) reproduce its
construction without placing API credentials, archives, adapted inputs, or
proof blobs in this repository.

This study measures individual PIE proofs. It does not include Starknet PIE
generation, scheduling, wrapping, or aggregation into a recursive root. The
[separate tree-scaling study](../cuda-ingress-tree-scaling-h200-20261001/README.md)
used repeated verified leaves and is explicitly synthetic.
