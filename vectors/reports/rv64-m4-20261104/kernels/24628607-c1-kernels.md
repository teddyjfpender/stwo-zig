# kernels c1: 3-pass log-24 NTT + row-major DEEP aggregation (24628607, 2x RTX 5090)

Proofs are byte-identical to the M3 integrate scale receipts: 55/55 hashes on 24628607 and 37/37 on 26235156. The fresh
receiver accepted both blocks. Kernel times come from nsys, one observation each, with the pod's 1-minute load average
at 42-47 **[M]**. Bandwidth and occupancy are derived **[D]**. Nsight Compute cannot run on this pod (`ERR_NVGPUCTRPERM`),
so achieved bandwidth is exact traffic divided by duration, and occupancy is theoretical from `cuobjdump -res-usage`.

## What changed
- **Fewer passes.** Each pass was already near the bandwidth roof (82-86% of peak), so the only lever left was the
  pass count. The 8-stage continuation was excluded from logs 20-26 because its 16 values lived in a 64-byte local
  stack. The cause was dynamic indexing: the second stage loop ran to the runtime `max_stage`, so nvcc could not
  unroll it. With compile-time trip counts the stack is 0 bytes (72 regs at 1 CTA/SM, or 64 regs at 2 CTAs/SM; they
  measured equal). Logs 24/25/26 now use {8,8,8}/{8,8,9}/{8,8,10}, which is 3 HBM passes instead of 4.
  - **Why the output is identical:** every partition of the stages computes the same butterfly sequence.
  - **Check:** the microbenchmark is identical on random data for logs 16, 18, 24, 25 and 26, in both N2B and LDE
    modes.
- **DEEP aggregation is now row-major.** One thread owns 2 rows and all 8 OM31 coordinates. Each coefficient is
  loaded once instead of 8 times. The term -> source -> tree pointer chain is resolved once per CTA chunk, in shared
  memory. Products (< 2^62) accumulate lazily in u64 and fold every 2 terms.
  - **Why the output is identical:** M31 addition is exact, so the canonical result does not depend on the order of
    terms.
  - **Rollback:** `STWO_RV64_DEEP_COORDINATES=1` restores the M3 kernel for A/B runs.

Request walls on this loaded pod (load avg 42-47) are noise-dominated. They are recorded in the progress rows, but are
not claimed as a speedup here. The recursion stage stays host-bound (see `TIMELINE.md`), so kernel savings move wall
time only where they sit on a lane's critical path.
