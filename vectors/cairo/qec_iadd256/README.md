# Fixed iadd256 Cairo proof experiment

`generate.py` compiles the public, SHA-256-pinned `iadd256.kmx` CX/CCX gate
sequence into a Cairo executable and generates one batch of 64 bit-sliced
inputs from `SHAKE256(raw KMX bytes)`. The executable applies all 2,547 gates
per repetition. It then computes the expected 256-bit addition with a separate
bit-sliced carry loop and asserts the target and offset results before
publishing all 512 qubit words. Its gate table is accepted only after the
generator checks the exact public fixture hash, complete two-register layout,
operation counts and qubit indices.

The Cairo proof covers gate execution and the in-program result checks. The
SHAKE-derived inputs are generated by the host and passed as public executable
arguments; Cairo does **not** verify their derivation from private circuit
bytes. This is a fixed-fixture, one-batch diagnostic rather than the complete
9,024-shot/8,000-repetition statement or a recursive root.

From the repository root, using Scarb 2.18.0 and the release-built Zig Cairo
CPU product:

```sh
python3 vectors/cairo/qec_iadd256/generate.py \
  --out /tmp/qec-cairo-iadd256 --total-shots 64 --batch 0 --repetitions 1
(cd /tmp/qec-cairo-iadd256 && scarb build)
zig build stwo-cairo-cpu -Doptimize=ReleaseFast
zig-out/bin/stwo-cairo-cpu run-and-prove \
  --program /tmp/qec-cairo-iadd256/target/dev/qec_iadd256.executable.json \
  --program-type executable --arguments /tmp/qec-cairo-iadd256/args.json \
  --proof /tmp/qec-cairo-iadd256/proof.json \
  --report-out /tmp/qec-cairo-iadd256/report.json --verify
cargo run --release --manifest-path tools/stwo-cairo-official-verifier-rs/Cargo.toml -- \
  verify --proof /tmp/qec-cairo-iadd256/proof.json --channel blake2s \
  --proof-format json --result /tmp/qec-cairo-iadd256/verdict.json
cargo run --release --manifest-path tools/stwo-cairo-official-verifier-rs/Cargo.toml -- \
  inspect-blake2s-proof-public-statement \
  --proof /tmp/qec-cairo-iadd256/proof.json \
  --result /tmp/qec-cairo-iadd256/statement.json
python3 vectors/cairo/qec_iadd256/check_proof_output.py \
  --proof /tmp/qec-cairo-iadd256/proof.json \
  --expected /tmp/qec-cairo-iadd256/expected.json \
  --verdict /tmp/qec-cairo-iadd256/verdict.json \
  --statement /tmp/qec-cairo-iadd256/statement.json
```

The output checker requires an official Rust-verifier verdict for the *same*
proof hash, the pinned compiled-program root, q70/26 proof parameters, and
exact equality of all 512 ordered
public output words with the independent bit-sliced Python oracle. A changed
CX target made Cairo execution panic with `wrong target`; a changed expected
output was rejected by the output checker. Both negative tests used the same
generated one-repetition batch.

## Measured local rung

One M1 macOS ReleaseFast observation at 64 shots and one repetition produced a
real Zig Cairo proof accepted by both Zig and the pinned official Rust
verifier. The proof config records 70 FRI queries and 26 PoW bits. Scarb
execution took 36,935,007 Cairo steps. From executable/arguments to verified
proof publication, the Zig command took 20.993 s: 3.485 s execution, 17.024 s
proving and 0.010 s Zig verification, with other preparation/encoding in the
remainder. The prover's lifetime physical footprint peaked at 29.464 GB. The
JSON proof was 3,682,553 bytes. These are one observation and one host, not a
cross-route speed claim. A two-repetition **execution-only** run took
73,467,522 Cairo steps; it has no proof timing.

The generated Cairo source SHA-256 was
`0ecd4de9ddc80f3082eed01fe07a269835f4a545eaab3c057b95aff72555be91`.
The compiled executable SHA-256 was
`74d604daf933c73fb08b4da1f1789e6226485c2640dbb3a986087ea5f97d38aa`.
The independently inspected proof program root was
`a9e2a56aa041c583b124df4455f94085ee76426e8f13b287484ef117dd799b75`.
The verified proof SHA-256 was
`f11d66edc89ceb1e4a8f35373572db65a88589c3c348a900117a5d6bfeaee465`.
The source, arguments and independent expected values regenerate from the
checked-in public fixture; large build, PIE and proof artifacts stay out of Git.
The saved numerical observation is in `measurements.tsv`.

The Scarb-generated PIE for this run was 117 MB and the repository's PIE
adapter rejected its `memory.bin` size. The executable route above completed
and proved the same generated Cairo program directly. A production PIE route
would need separate adapter-capacity work; this diagnostic does not raise
that cap implicitly.
